# Kepos V1 Dependency Order

This document orders V1 work by architecture dependency.

The V1 principle is: build slower if needed, but do the right architecture first. Do not ship a shortcut as product architecture if it creates a hard migration or weak security boundary.

## 1. Identity Foundation

### 1.0 Research And Library Selection Gate

Before implementing protocol-critical crypto or encoding, query current open source options and prefer maintained community libraries over custom code.

Required research areas:

- Ed25519 signing and verification
- canonical JSON or deterministic binary encoding for signed records
- identity key derivation compatible with Holepunch/Keet direction
- QR encoding/decoding for React Native and desktop
- encrypted DM invite payloads
- local secure-enough persistence per platform

Selection criteria:

- actively maintained
- compatible with Node
- compatible with Bare Android backend
- does not break React Native bundling
- small and understandable API
- license compatible with Kepos
- testable without network services

Do not hand-roll cryptography, signature formats, QR generation/parsing, or canonical serialization if a good library exists.

Current V1 baseline from research:

- language: new protocol/domain modules should be TypeScript-first when the module is not directly loaded by browser/Electron renderer without a verified loader; existing JS/JSX/MJS runtime glue stays in place until migration is worth it
- TypeScript boundary: see `docs/v1.05-typescript-boundary.md`
- signing: `hypercore-crypto`
- signed bytes: fixed `compact-encoding` schemas
- fallback signing: `@noble/ed25519` if React Native or mobile bundling blocks the Holepunch sodium path
- DM invite encryption: libsodium sealed boxes through `sodium-universal`/`sodium-native`
- QR mobile display: `react-native-qrcode-svg`
- QR mobile scan: `expo-camera`
- QR desktop render: `qrcode`
- desktop camera scan: deferred; likely later path is `@zxing/browser`
- persistence: versioned JSON files plus existing Corestore/Autobase directories

Before implementation, run compatibility probes for:

- `hypercore-crypto` keypair/sign/verify in Node
- `hypercore-crypto` keypair/sign/verify in Bare Android backend bundle
- `compact-encoding` signed payload test vectors in Node and Bare Android
- `sodium-universal` sealed box encrypt/decrypt in Node and Bare Android
- React Native boundary: keep secrets in backend; pass only public keys, signed records, and ciphertext through UI bridge

Current probe status:

- Node probe passes through `npm run compat:probe`.
- Node test passes through `node --test test/compatibility-probes.test.js`.
- Android Bare backend bundle passes through `npm run compat:bundle:android`.
- Android device runtime execution is covered by `npm run smoke:android` and targeted debug two-device runs when they pass. Physical QR release proof has passed for desktop Large Profile QR and Large Home QR screen-to-camera smoke into Android trust and trusted-only home join.
- TypeScript probe passes through `npm run compat:typescript`.
- TypeScript Android Bare backend bundle passes through `npm run compat:bundle:typescript`.

Current implementation status:

- `src/signed-record.ts` provides the shared signed-record utility using `hypercore-crypto`, fixed `compact-encoding` payload schemas, and explicit TypeScript types.
- `test/signed-record.test.js` covers verify success, payload tamper failure, and signer mismatch failure.
- `scripts/probe-signed-record-types.ts` keeps the signed-record type boundary covered by `npm run typecheck`.
- `src/identity.js` now creates identity keys through `hypercore-crypto`, so local profile ids are backed by matching Ed25519 signing secret keys.
- `test/identity.test.js` proves generated identities can sign and verify records under their profile id.
- The utility is not imported from the React Native UI path.
- `src/dm-invite.ts` and `src/message-request.ts` now own typed DM bootstrap records, sealed invite payloads, and one-message request proof validation.
- `scripts/probe-dm-bootstrap-types.ts` keeps the DM bootstrap type boundary covered by `npm run typecheck`.
- `src/trust-grant.ts` and `src/signed-qr-payload.ts` now own typed trust grants, signed profile QR payloads, signed home QR payloads, and QR URI route matching.
- `scripts/probe-trust-qr-types.ts` keeps the trust/QR type boundary covered by `npm run typecheck`.
- `src/contact-book.ts` and `src/dm-thread.ts` now own typed durable local trust state, pending request state, and accepted/revoked DM thread state.
- `scripts/probe-durable-state-types.ts` keeps the durable state type boundary covered by `npm run typecheck`.
- `src/treehole-policy.ts` now owns typed treehole session-mode selection, signed policy defaults, and writer-grant policy. Autobase runtime wiring remains in JavaScript.
- `scripts/probe-treehole-policy-types.ts` keeps the treehole policy type boundary covered by `npm run typecheck`.
- `tsconfig.json` and `npm run typecheck` are active for new TypeScript modules.
- TypeScript is proven for shared Bare/Node-compatible modules through `src/treehole-signed-events.ts`, `npm run compat:typescript`, and `npm run compat:bundle:typescript`.
- Browser/Electron-renderer-loaded modules should move to TypeScript only after their loading path is verified; otherwise keep runtime glue in JS and move protocol logic behind tested shared modules.
- Existing JavaScript protocol modules should migrate gradually when touched for meaningful new behavior. Do not keep adding security-sensitive record shapes to JavaScript when a new TypeScript domain module can own the shape.
- Migration order for existing JS protocol modules is recorded in `docs/v1.05-typescript-boundary.md`.

### 1.1 Define Identity As The Root

`profile.id` is the identity public key.

Required:

- stable local identity public key
- stable local identity secret key
- profile id equals identity public key
- profile id is backed by the matching signing secret key
- identity survives app restart
- desktop and Android use the same shared domain model

V1 does not require:

- seed phrase
- account recovery
- multi-device identity
- device attestation

### 1.2 Add Real Signing And Verification

V1 must include real signing for protocol-critical records.

Required:

- sign bytes or canonical JSON
- verify signature against identity public key
- reject malformed signatures
- shared API usable by Node, desktop, Bare Android backend, and React Native-safe paths

Records that need signing:

- home address payload
- trust grant
- DM invite
- message request
- treehole post/comment/like/delete events

### 1.2.1 Choose Signing Library

Use `hypercore-crypto` as the V1 signing baseline if compatibility probes pass.

Keep `keet-identity-key` as the later Keet-grade identity path for mnemonic/root identity and device attestation.

Keep `@noble/ed25519` as the React Native-friendly fallback if the Holepunch sodium path cannot run in the required mobile boundary.

Selection criteria:

- works in Node
- works in Bare Android backend
- does not break React Native bundling
- can verify from shared source code
- can serialize keys and signatures cleanly

### 1.2.2 Define Canonical Signed Envelope

All signed protocol records should have one envelope shape.

```js
SignedRecord {
  type,
  version,
  payload,
  signerProfileId,
  createdAt,
  signature
}
```

The signed bytes must be deterministic. V1 should use fixed `compact-encoding` schemas for signable payloads and keep canonical JSON only as a debug/migration fallback.

Do not sign ad hoc JSON string output.

### 1.3 Persist Identity Safely Enough For V1

Required:

- desktop local persistence
- Android app-private persistence
- no accidental regeneration on restart
- no logging secret keys

Not required for V1:

- OS secure enclave
- biometric unlock
- seed phrase export

## 2. ContactBook And Trust

### 2.1 Create Shared ContactBook Domain Model

ContactBook belongs to the local identity.

```js
ContactBook {
  ownerProfileId,
  contacts: [
    {
      profileId,
      alias,
      displayNameSnapshot?,
      homeAddress?,
      homePolicy?,
      trustedAt?,
      revokedAt?,
      source,
      proof?
    }
  ]
}
```

Current implementation status:

- `src/contact-book.ts` provides pure typed ContactBook domain helpers for contact upsert, local alias, trust, revoke, pending message request, request acceptance, home access, and presence policy.
- `src/contact-book.ts` serializes/deserializes versioned ContactBook JSON and creates treehole policy snapshots from trusted/revoked contacts.
- `test/contact-book.test.js` covers local owner binding, alias behavior, trust/revoke, one pending message request, revoked request rejection, no access from requests, accepting a request into trust, JSON roundtrip, and treehole policy extraction.

### 2.2 Persist ContactBook Per Platform

Required:

- desktop adapter
- Android adapter
- migration/version field
- tests for persistence and reload

Current implementation status:

- `src/contact-book-storage.js` provides sync key-value storage helpers for desktop/localStorage-style stores.
- `src/contact-book-storage.js` provides async file storage helpers for Android app-private FileSystem-style stores.
- ContactBook file storage initializes only missing files as empty state and fails closed on corrupt storage.
- `test/contact-book-storage.test.js` covers save/load, missing-file initialization, and corrupt-file rejection.

V1 does not sync ContactBook across devices.

### 2.3 Alias At Trust And Request Boundaries

Creating trust or accepting/replying to a message request should create or confirm a local alias for the other profile.

Rules:

- QR display name is only a suggestion
- alias is local and user-editable
- alias is stored in ContactBook
- remote signed profile metadata must not overwrite alias without user intent

### 2.4 Sign Trust Grants

Trust is the authorization SSOT.

```js
TrustGrant {
  ownerProfileId,
  trustedProfileId,
  scope: 'home',
  createdAt,
  revokedAt?,
  proof
}
```

`proof` must verify against `ownerProfileId`.

Current implementation status:

- `src/trust-grant.ts` creates and verifies signed V1 home trust grants.
- `applyTrustGrantToContactBook()` verifies a grant before writing trust into ContactBook.
- signed profile QR import creates a local owner-signed trust grant proof when the local identity is available.
- `test/trust-grant.test.js` covers valid grants, tamper rejection, and safe ContactBook application.

### 2.5 Enforce Trust In Shared Policy Code

One shared policy module should answer:

- can enter home
- can read treehole
- can comment
- can like
- can open DM
- can send one message request
- can see presence

Keys are transport capabilities, not permission.

## 3. Home And QR

### 3.1 Owner-Bind Home

Required invariants:

- one profile owns one home room
- `home.ownerProfileId === profile.id`
- `home.address` is shareable
- `home.roomKey` is transport capability
- trusted-only policy uses ContactBook/trust

### 3.2 Sign Home Address Payload

Home QR should carry a signed payload.

```js
HomeAddressPayload {
  type: 'kepos.home.address.v1',
  ownerProfileId,
  address,
  roomKey,
  policy,
  createdAt,
  proof
}
```

Current implementation status:

- `src/signed-qr-payload.ts` creates and verifies signed profile trust invite payloads and signed home address payloads.
- Signed profile and home QR payloads support optional signed `expiresAt`; stale QR fails verification before trust or join.
- It also provides V1 URI envelope helpers: `kepos://profile?v=1&payload=...`, `kepos://home?v=1&payload=...`, and `kepos://message-request?v=1&payload=...`.
- `test/signed-qr-payload.test.js` covers signed profile, home, and message-request payload round trips through their V1 URI routes.
- `src/signed-qr-scan.js` verifies signed profile QR URIs and writes trusted contacts into ContactBook with local alias fallback.
- `src/signed-qr-scan.js` verifies signed home QR URIs and returns join metadata with local public/trusted-only access checks.
- Desktop and Android lobby UI can display local signed profile and home URIs.
- Desktop renders signed profile and home URIs as real SVG QR codes through `qrcode`.
- Android renders signed profile and home URIs through `react-native-qrcode-svg`.
- Android scans profile and home QR codes through `expo-camera`, then routes scanned data through the existing signed QR validation and trust/home join flows.
- `src/mobile-qr-actions.js` owns the testable Android scan action boundary; `test/mobile-qr-actions.test.js` verifies profile scans accept only signed profile QR payloads and home scans preserve the signed home trust gate result.
- Desktop and Android lobby UI can import another signed profile URI into persisted ContactBook.
- Desktop and Android lobby UI can import a signed home URI and join when it is public or locally trusted.
- Existing raw JSON QR helpers remain as prototype compatibility and test/debug paths.

### 3.3 Use URI-Wrapped QR Payloads

V1 QR format:

```text
kepos://profile?v=1&payload=<encoded-json>
kepos://home?v=1&payload=<encoded-json>
kepos://message-request?v=1&payload=<encoded-json>
```

Raw JSON remains test/debug only.

## 4. Treehole Authorization

### 4.1 Owner-Bind Treehole

Required:

- one treehole per profile
- treehole owner is profile id
- storage path is app-private
- storage is stable across restart

### 4.2 Sign Treehole Events

Every treehole event must be signed by its author.

Required event families:

- post create
- post delete tombstone
- comment create
- comment delete tombstone
- like add
- like remove
- writer grant

Current implementation status:

- `src/treehole-signed-events.ts` provides signed post, post tombstone, comment, comment tombstone, like add/remove, and writer grant constructors.
- `applySignedTreeholeEvents()` enforces owner-only posts, trusted comment/like writes, tombstones, like toggles, revoked writer rejection, and signature verification.
- `test/treehole-signed-events.test.js` covers owner-only posts, trusted comments/likes, stranger rejection, like remove, comment tombstone, post tombstone, writer grant signature binding, and tamper rejection.
- `src/treehole-base.js` now has `mode: 'signed'` for Autobase-backed signed post, comment, like/unlike, post tombstone, comment tombstone, and writer grant appends.
- `test/treehole-base.test.js` covers signed Autobase owner posts, trusted comment/like writes, non-owner post rejection, owner comment deletion, signed writer grants, and unsigned writer grant rejection in signed mode.
- `src/treehole-policy.ts` centralizes treehole session option selection and chooses signed mode only when identity and owner profile id are available.
- `src/treehole-view.js` serializes posts with embedded comments for desktop and Android UI/RPC payloads.
- Desktop and Android backend callers now pass identity and owner profile data into the shared treehole session helper.
- Desktop and Android UI now expose treehole text posts, comments, and likes.
- The default `createTreeholeBase()` mode remains unsigned prototype compatibility for debug and incomplete identity contexts.

### 4.3 Enforce Event Policy In Reducer

Rules:

- main post create requires author equals treehole owner
- post tombstone requires actor equals treehole owner
- comment create requires trusted author
- like add/remove requires trusted author
- comment delete requires comment author or treehole owner
- malformed or unauthorized events are ignored

### 4.4 Add Writer Grants After Trust

Trusted users can comment/like, but writer authorization should be lazy.

First comment/like may trigger writer authorization. The grant must not allow main posts from non-owner because reducer policy still checks event type and signature.

Current implementation status:

- signed mode writes `treehole.writer.grant.v1` as an owner-signed audit event before adding an Autobase writer.
- signed mode rejects writer grants without the writer profile id and ignores legacy unsigned `treehole.writer.add`.
- Desktop and Android callers now load local ContactBook snapshots and pass treehole trust policy into signed treehole sessions.
- Desktop and Android writer grant handling now checks writer profile id against the local owner policy before adding an Autobase writer.
- Profile URI import now creates persisted trusted contacts. QR image display and Android camera scan UX exist. `test/qr-rendering.test.js` proves generated signed profile/home QR PNGs decode through `jsQR`. Debug two-device smoke is the intended live room, treehole, DM, restart, and desktop revoke path; Android smoke covers scanner open/cancel. The screen-to-camera QR proof has passed for desktop Large Profile QR and Large Home QR scanned into Android trust and home join for the current release candidate.

## 5. DM And Message Requests

### 5.1 Define MessageRequest

Untrusted sender can send one request.

```js
MessageRequest {
  requestId,
  fromProfileId,
  toProfileId,
  senderEncryptionPublicKey,
  text,
  createdAt,
  proof
}
```

A pending request grants no read, presence, home, treehole, or DM access.

Current implementation status:

- `src/message-request.ts` creates and verifies signed one-message requests.
- `applyMessageRequestToContactBook` records one pending request per untrusted sender.
- ContactBook rejects new pending requests from revoked contacts.
- message requests carry the sender DM encryption public key so replies can be sealed without another key exchange.
- home room protocol now accepts `kepos.message.request.v1` as a setup/control frame.
- desktop and Android can send message requests through the existing room control path.

### 5.2 Define Signed And Encrypted DmInvite

Final V1 architecture uses explicit invites, not deterministic pair topics.

V1 baseline encryption is libsodium sealed boxes over the private invite payload, with identity signing on the public invite fields. Signing and encryption keys should be separate.

```js
DmInvite {
  type: 'kepos.dm.invite.v1',
  inviteId,
  fromProfileId,
  toProfileId,
  channelPublicKey,
  channelDiscoveryKey,
  createdAt,
  expiresAt?,
  requestId?,
  proof,
  encryptedPayload
}
```

Current implementation status:

- `src/dm-invite.ts` creates a separate DM encryption key pair with `sodium-universal`.
- invite public routing fields and ciphertext are identity-signed.
- private invite payload is encrypted with libsodium sealed boxes for the recipient encryption public key.
- tests cover successful open by the recipient key and rejection after routing-field tampering.
- `src/message-request-acceptance.js` turns a pending request into trust, a sealed invite, and an accepted local thread, while rejecting revoked contacts.
- `src/dm-invite-acceptance.js` opens a valid invite into an accepted recipient thread.

### 5.3 Persist Durable DmThread

```js
DmThread {
  threadId,
  localProfileId,
  remoteProfileId,
  channelPublicKey,
  channelDiscoveryKey,
  createdAt,
  acceptedAt?,
  revokedAt?,
  requestId?
}
```

Current implementation status:

- `src/dm-thread.ts` models pending, accepted, and revoked threads.
- `src/dm-thread-storage.js` stores versioned thread collections in localStorage-style and app-file-style storage.
- DM thread file storage initializes only missing files as empty state and fails closed on corrupt storage.
- desktop persists setup-created threads locally.
- Android persists setup-created threads through the React Native file storage adapter.

### 5.4 Keep DM Messages Off Home Room

Home room may carry setup notifications, but production DM message contents must use the pairwise DM channel.

Current implementation status:

- `src/protocol.js` rejects `dm` body frames.
- `src/p2p-room.js` no longer exposes `sendDirectMessage`.
- existing DM tab now displays message requests as setup records, not a production DM thread.
- desktop and Android can accept an incoming message request, create local trust, create a sealed DM invite, and persist the accepted thread.
- incoming DM invites are accepted only from trusted contacts or as request-bound acceptance responses, and revoked senders are rejected.
- Android keeps DM invite crypto in the Bare backend; the React Native UI only passes public keys, signed records, ciphertext, and thread metadata.
- `metro.config.cjs` maps `sodium-native` to `sodium-javascript` so Expo can bundle the signed QR path while DM invite crypto stays out of React Native UI code.
- desktop and Android backend now route signed DM bodies over dedicated accepted-thread DM replication channels instead of the home room.

Current V1 evidence:

- physical QR release proof passed for screen-to-camera profile/home decode quality on the current desktop-to-Android path

### 5.5 Sign DM Messages

```js
DmMessage {
  id,
  threadId,
  fromProfileId,
  text,
  createdAt,
  proof
}
```

Proof must verify against `fromProfileId`.

Current implementation status:

- `src/dm-message.ts` creates and verifies signed `kepos.dm.message.v1` records.
- message proof uses fixed `compact-encoding` signed bytes through the shared signed-record helper.
- verification rejects payload tampering and signer/from-profile mismatch.
- `src/dm-message-storage.ts` stores verified signed messages per thread for localStorage-style and app-file-style storage.
- message storage rejects tampered records and corrupt files, dedupes by `messageId`, and sorts by creation time.
- `src/dm-replication.js` provides a dedicated DM Hyperswarm channel over a topic derived from the thread's `channelDiscoveryKey`.
- the DM replication channel only accepts signed `kepos.dm.message.v1` records for the joined thread and ignores tampered, duplicate, self-authored, or wrong-thread frames.
- `src/dm-session.js` can append signed DM messages into the existing desktop/mobile display session shape.
- `src/dm-thread-runtime.js` opens accepted DM threads, replays stored messages, persists sent/received messages, and emits UI-friendly send/receive callbacks.
- desktop opens accepted DM threads, sends signed DM bodies over the dedicated DM channel when a recipient already has an accepted thread, and falls back to message request otherwise.
- Android backend opens accepted DM threads inside Bare, persists thread/message state with Bare fs adapters, and exposes signed DM body send/receive through dedicated RPC commands.
- `src/contact-book.ts` exposes trusted contacts as DM recipient options, and desktop/mobile DM composers can select trusted contacts before falling back to manual profile id entry.

Remaining polish:

- refine full contacts view after V1 smoke if needed

## 6. Revocation

### 6.1 Revoke Trust

V1 revoke blocks future access but does not delete already replicated data.

Required:

- set `revokedAt`
- reject trusted-only actions after revoke
- stop new treehole writer grants
- stop new DM invites
- mark affected DM threads closed/revoked

### 6.2 Do Not Auto-Rotate Keys In V1

V1 does not automatically rotate home, treehole, or DM keys after revoke.

This limitation is accepted because key rotation affects QR, discovery, writer state, and existing peers.

## 7. Cross-Platform Parity

### 7.1 Shared Domain Tests

Required:

- identity signing
- signed envelope validation
- ContactBook
- trust policy
- QR encode/decode
- treehole reducer authorization
- DM invite validation
- message request limit

### 7.2 Desktop Smoke

Required:

- identity persists
- ContactBook persists
- trust profile
- join home
- room chat
- treehole post/comment/like/delete
- DM request/invite/thread

### 7.3 Android Smoke

Same as desktop, using app-private storage and Bare backend paths.

## Dependency Summary

```text
1. Library research and compatibility probes
  -> 2. Identity signing and signed-byte envelope
  -> 3. Signed trust / ContactBook
  -> 4. Signed home/profile/message-request QR
  -> 5. Signed treehole events
  -> 6. Signed + encrypted DM request/invite/messages
  -> 7. Revoke enforcement
  -> 8. Desktop + Android parity
```

Do not implement treehole multi-writer comments or production DM before identity signing exists.
