# V2 Watch Room

This document records the V2D direction for Kepos watch rooms.

The decision is deliberately narrow: the first watch room is a trusted shared
viewing session. It is not a meeting product.

V2 watch rooms should support self-hosted video where possible and desktop live
streaming where needed. Kepos handles trust, session state, P2P access or
delivery, and playback coordination.

## Decision

Kepos V2D should model a watch room as one of two source paths.

Self-hosted video source:

```text
Jellyfin, Plex, or Emby
  -> Kepos local P2P proxy
  -> trusted viewer playback
```

Desktop live stream source:

```text
OBS or compatible producer
  -> localhost ingest
  -> Kepos P2P media stream
  -> trusted viewer playback
```

The first version supports:

- 1 host
- 1 viewer
- desktop first
- self-hosted video source, when the media already lives in a library
- OBS-compatible local ingest, when the media is not easy to download, record,
  or serve from a library
- room chat remains available

The first version does not support:

- multiple viewers
- cameras
- viewer microphone
- microphone mixing
- recording
- SFU
- public links
- meeting controls

## Why

The product goal is closer to:

```text
I am watching something; one trusted friend can watch with me.
```

It is not:

```text
Replace Zoom or Tencent Meeting.
```

This keeps the feature aligned with Kepos home:

- explicit trusted relationship
- private room
- no platform meeting room
- no public broadcast
- no extra account graph

It also keeps the first technical surface small. One outgoing media stream is
much easier to reason about than multi-viewer conferencing.

Using a self-hosted video service keeps Kepos from owning media libraries,
metadata, subtitles, transcoding, and format handling.

Using OBS-compatible local ingest keeps Kepos from owning all screen capture and
audio mixing work when the source is a desktop stream. OBS already knows how to
capture windows, screens, system audio, microphone input, scenes, and overlays.
Kepos can focus on trusted delivery.

## Relationship To V2 Shared Music Room

V2B shared music room is:

```text
self-hosted music service -> shared queue -> synchronized room playback
```

V2D watch room is:

```text
self-hosted video service or desktop live stream -> shared viewing session
```

The two features should share ideas where possible:

- session state
- host-owned room lifecycle
- trusted join
- local P2P access or dedicated media stream channel
- room chat separate from media payloads
- no recording by default

But watch room adds self-hosted video integration and, for the live source path,
screen/window capture and video encoding through OBS or a compatible producer.

## Scope

In scope:

- desktop host
- desktop viewer
- trusted viewer only
- one active viewer per watch room
- self-hosted video service source
- local media ingest from OBS or an OBS-compatible producer
- shared playback state for library media
- encoded audio/video stream for live desktop media
- viewer playback
- room chat alongside the stream
- explicit stop/close

Out of scope:

- mobile host
- mobile viewer
- more than one viewer
- viewer video
- viewer microphone
- multi-party voice
- recording or replay
- public invite links
- meeting lobby
- screen annotation
- remote control
- file transfer

## Session Shape

```ts
type WatchRoomSession = {
  type: 'kepos.watch-room.session.v1'
  version: 1
  sessionId: string
  homeOwnerProfileId: string
  hostProfileId: string
  viewerProfileId: string
  sourceType: 'self_hosted_video' | 'local_ingest'
  source?: {
    service: 'jellyfin' | 'plex' | 'emby' | 'generic_http'
    itemId?: string
    streamUrl?: string
  }
  playback?: {
    status: 'playing' | 'paused'
    startedAtRoomTime: number
    positionMsAtStartedAt: number
    version: number
  }
  video: {
    codec: 'h264' | 'vp8' | 'vp9' | 'av1'
    maxWidth: number
    maxHeight: number
    maxFps: number
  }
  audio: {
    codec: 'opus'
    sampleRate: 48000
    channels: 2
  }
  state: 'invited' | 'connecting' | 'playing' | 'stopped' | 'failed'
  createdAt: number
  startedAt?: number
  stoppedAt?: number
}
```

Session records that affect state should be signed by the host profile.

## Media Paths

Self-hosted video target path:

```text
Jellyfin, Plex, Emby, or generic HTTP video source
  -> owner Kepos local P2P proxy
  -> viewer Kepos local proxy
  -> viewer player
```

Kepos should keep shared control state, such as play, pause, seek, and current
item. The self-hosted service keeps the media library, subtitles, metadata, and
transcoding behavior.

Desktop live stream target path:

```text
OBS or compatible producer
  -> localhost ingest
  -> Kepos media packetizer
  -> Kepos P2P media stream
  -> viewer decoder/playback
```

For the live stream path, the first implementation should prefer forwarding
already encoded A/V from the ingest path. Kepos should avoid decoding and
re-encoding unless a later implementation proves it is needed.

The room chat remains separate:

```text
room chat frames != media frames
```

## Product Rules

- only a trusted contact can be invited as viewer
- only one viewer can join in v1
- host owns start and stop
- host leaving closes the watch room
- viewer leaving closes or returns the room to stopped state
- no recording UI in v1
- no public share link in v1
- self-hosted library media is shared through an explicit room-scoped service
  share
- desktop stream media is live and ephemeral

## Technical Questions

Before implementation, investigate:

- best local ingest protocol for OBS-compatible input: RTMP, SRT, or WHIP
- whether Kepos can forward encoded A/V without transcoding
- whether WebRTC should be used for viewer playback or whether Kepos should send
  encoded frames over its own P2P channel
- how much control can be done through Jellyfin, Plex, or Emby APIs without
  exposing broad server access
- how to sync video playback state without fighting the self-hosted player's own
  buffer and transcoding behavior
- codec availability across target desktop platforms
- minimum viable bitrate and latency for 720p / 30fps
- how to surface ingest connection, stream start, and stream failure states
  cleanly

The first implementation should not depend on solving multi-viewer bandwidth or
SFU design.

## Implementation Order

1. Session model

   Add the watch room session state and signed host control records.

2. Self-hosted video probe

   Share one Jellyfin, Plex, Emby, or generic HTTP video item through the local
   P2P proxy and coordinate play, pause, and seek state.

3. Local ingest probe

   Accept one OBS-compatible localhost stream and play it locally.

4. One-viewer media stream

   Forward the ingested encoded A/V stream to one trusted viewer over a
   dedicated media stream channel.

5. Home UI

   Show invite, connecting, playing, stopped, and failed states in the home.

6. Hardening

   Handle ingest not connected, ingest ended, viewer disconnect, host stop,
   network failure, and revoke.

## Success Bar

V2D is useful when:

- Neil invites Ada to watch from a trusted home.
- Neil chooses either a self-hosted video item or an OBS-compatible desktop
  stream.
- Ada sees the same video.
- Ada hears the same audio.
- room chat still works.
- Neil stops sharing and the room closes cleanly.

The first version succeeds without meetings, cameras, microphones, recording,
public links, or more than one viewer.
