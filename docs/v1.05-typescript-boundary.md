# Kepos TypeScript Boundary

This document defines where V1 should use TypeScript.

## Decision

New protocol and domain modules should be TypeScript-first.

Platform runtime glue can stay JavaScript until its loader path is proven.

## Why

Kepos V1 has security-sensitive state:

- identity keys
- signed records
- trust grants
- home access policy
- treehole events
- DM requests, invites, threads, and messages
- QR payload schemas

These shapes should be explicit and checked. Plain JavaScript is too easy to drift when several platforms share the same rules.

## Use TypeScript Now

Use TypeScript for pure shared modules under `src/` when they are not directly loaded by a fragile runtime path:

- identity and signed-record helpers
- trust and ContactBook model
- home access policy
- treehole signed event schemas and reducers
- DM request, invite, thread, and message schemas
- QR payload schemas and parsers
- versioned local storage envelopes

Every new TypeScript module must pass:

- `npm run typecheck`
- `npm run compat:typescript` when it is shared protocol logic
- `npm run compat:bundle:typescript` when it must work in the Bare Android backend

## Keep Platform Edges Gradual

Keep these as platform runtime edges until their loading path and type surface
are verified:

- `backend/backend.mjs`
- `desktop/app.tsx`
- `desktop/controller.js`
- `mobile/App.tsx`
- Electron renderer entry code
- Bare worklet entry code
- React Native UI glue

These files should call shared typed modules instead of owning protocol rules.

## Migration Rule

Do not rewrite everything to TypeScript in one pass.

When touching an existing JavaScript protocol/domain module for meaningful new behavior, prefer one of these:

1. Move the changed protocol shape into a new TypeScript module and keep a thin JS caller.
2. Convert the module to TypeScript if all import paths are already proven by tests, Node execution, and Android bundle probes.
3. Leave the file in JavaScript only when the change is small and the module is on a fragile platform path.

The direction is TypeScript for shared rules, JavaScript for platform edges.

## Import Specifier Rule

Use the import form that matches the runtime that will load the emitted code.

For the current Kepos V1 shared TypeScript graph, use explicit `.ts` relative
imports between TypeScript source modules:

```ts
import { createContactBook } from './contact-book.ts'
```

This is intentional for the current toolchain. `tsconfig.json` typechecks with
`noEmit` and `allowImportingTsExtensions`, while the Bare/Android bundle config
uses `rewriteRelativeImportExtensions` when it emits JavaScript into
`tmp/bare-bundle-js`. Source imports stay honest about the source file, and the
emitted bundle gets JavaScript extensions before runtime loading.

For JavaScript and MJS runtime glue, keep explicit `.js`, `.mjs`, or `.cjs`
specifier forms that match the file being loaded:

```js
import { createDesktopCommandHost } from './desktop-command-host.ts'
```

Do not use extensionless relative imports in shared protocol, backend, worker,
or Electron runtime code. Node ESM, Bare, and the generated Android bundle all
benefit from explicit extensions.

For desktop React UI or other bundler-only code, extensionless local imports are
acceptable only when that specific bundler path has been verified:

```ts
import { HomePane } from './HomePane'
```

Mobile React TSX is the current exception. `tsconfig.json` uses NodeNext-style
resolution for source checking, so `mobile/*.tsx` keeps explicit `.js` local
specifier suffixes even when the source files are `.ts` or `.tsx`. Expo/Metro
does not resolve those source files by default, so `metro.config.cjs` maps only
local `.js` specifiers to sibling `.ts` / `.tsx` source files when they exist.
The V1 gate proves this with `npx expo export --platform android`.

Only prefer emitted `.js` specifiers inside a separate TypeScript package or
subgraph that is meant to be published or run directly as plain Node ESM output
without the current Kepos rewrite/bundle step. That is not the default V1 path.

## Migration Priority

Convert security-sensitive shared modules before convenience modules.

1. `src/signed-record.ts` (done)
   - core signed envelope, deterministic bytes, key validation, timestamp/version checks
   - everything else depends on this being stable
2. `src/dm-invite.ts` and `src/message-request.ts` (done)
   - DM bootstrap, sealed invite payloads, one-message request rules, signed request validation
   - mistakes here can leak private-message setup through the wrong trust boundary
3. `src/trust-grant.ts` and `src/signed-qr-payload.ts` (done)
   - trust creation, revoke payloads, profile QR, home QR, proof matching
   - this is the normal user-facing authority path
4. `src/contact-book.ts` and `src/dm-thread.ts` (done)
   - durable local trust state, request state, accepted/revoked DM thread state
   - these are central domain models and should become typed before they grow more fields
5. Policy slices from `src/treehole-policy.ts` (done)
   - Autobase/runtime glue can remain JS
   - signed event and writer-policy rules should move behind typed shared helpers

`src/identity.ts` already uses the same Ed25519 key shape as signed records. A profile id must be a public key backed by its matching secret key; do not recreate old public-id-only compatibility paths.

## Next Migration Candidates

The next TypeScript work should stay evidence-driven. Current source shape has
no JSX source files remaining: the desktop React renderer pieces and
`mobile/App.tsx` have been renamed to TSX, and generated bundles are excluded
from that source count. This does not mean the UI is fully typed yet:
`mobile/App.tsx` is now checked by TypeScript, while desktop TSX still depends
on runtime callback objects from the controller boundary. The useful path is to
keep moving pure shared rules and serialized shapes behind typed modules while
tightening UI component types in small slices.

The core V1 runtime path is now also typed at the source level:
`src/p2p-room.ts` owns Home room transport framing and debug snapshots,
`src/dm-replication.ts` owns the signed DM replication channel, and
`src/desktop-backend-session.ts` owns desktop backend session composition.
The remaining JavaScript files are entrypoints or platform glue, not unchecked
shared product logic.

`mobile/App.tsx` owns the remaining checked mobile runtime composition: React
state, QR scan handlers, Home join/create orchestration, direct-message request
handlers, treehole commands, and Bare RPC command dispatch. It keeps the
third-party Bare/RPC IPC edge behind local narrow types and normalizes inbound
RPC payloads before touching React state. Local TSX imports use explicit `.js`
specifier suffixes under the NodeNext TypeScript config; this is the runtime
ESM path, not a sign that the source file is JavaScript. Metro maps those
specifier suffixes to the checked `.ts` / `.tsx` mobile source files during Expo
Android export.

`src/mobile-runtime-ids.ts` owns checked mobile runtime ID helpers for Home room
keys and local message/thread ids. `mobile/App.tsx` still supplies Expo Crypto
and the optional platform UUID source, but secure random byte length, hex
encoding, and delegation to the shared secure-id utility now sit behind explicit
TypeScript functions instead of file-local unchecked helpers.

`src/mobile-profile-bootstrap.ts` owns checked mobile profile bootstrap and
backend storage base-path setup. `mobile/App.tsx` still supplies Expo FileSystem,
Expo Crypto identity/home-key factories, and runtime state setters, but durable
document-directory selection, `/kepos` backend storage directory creation,
profile document restore, identity restore/create, Home room key restore/create,
ContactBook restore, DM thread restore, recent-post cache restore, and initial
treehole policy derivation now sit behind explicit TypeScript functions instead
of file-local unchecked helpers.

`src/rpc-payload.ts` owns checked RPC request payload decoding for mobile and
other runtime edges. `mobile/App.tsx` still owns command-specific branching and
state updates, but empty request data handling, byte-to-string decoding through
`b4a`, and JSON parsing now sit behind an explicit TypeScript function instead
of a file-local unchecked helper.

`mobile/styles.ts` owns checked React Native style creation for the mobile app.
`mobile/App.tsx` still chooses the active theme and passes style objects to
runtime components, but `StyleSheet.create`, Android status-bar top padding,

token drift visible: avatar tone colors now require typed `success`, `warning`,
and `info` tokens in `src/mobile-theme-tokens.ts`.

`mobile/qr-components.tsx` owns checked QR card rendering for the React Native

Worth doing later, but not first:

- `mobile/App.tsx`
  - This is the largest remaining product file. It is now TSX without
    `@ts-nocheck`, with explicit state and RPC boundary types. Future slices
    should continue shrinking it by extracting cohesive state-model and command
    helpers, not by moving platform glue blindly.
- Desktop component modules such as `desktop/*-components.tsx`
  - They are already TSX and should be tightened next by extracting explicit
    props and action types at the React/controller boundary.
- Desktop command/action modules
  - `src/desktop-command-vocabulary.ts` and
    `src/desktop-command-registry.ts` are already typed. The remaining command

Keep as platform-edge glue for now:

- `backend/backend.mjs`
- `mobile/App.tsx`
- `backend/backend.mjs`
- `desktop/controller.js`
- Electron `main.cjs` / `preload.cjs`

These are entrypoints or operational glue. They should consume typed helpers
but should not be migrated or split merely for TypeScript coverage. Some are
already checked TSX; their status as platform-edge files means they should be
shrunk by extracting cohesive typed helpers, not rewritten wholesale.

## Release Proof Policy

Final V1 release proof is not blocked on a known TypeScript or implementation
gap. It is now a high-cost evidence step that should be run deliberately when
release confidence is needed, not as the default response to every small V1
code or docs change.

The release-proof smoke set is:

- `ANDROID_SERIAL=32131JEHN00865 npm run smoke:two-device:debug`
- `ANDROID_SERIAL=32131JEHN00865 npm run smoke:two-device:debug:pear`
- physical QR helper smoke when a human can aim the phone at the desktop QR

Routine implementation turns should prefer focused tests, typecheck, lint,
bundle gates, and docs-state tests. Do not run high-cost smoke unless the user
asks for smoke, release proof is the actual task, or the change touches a live
cross-device/runtime path that cannot be proven otherwise. If a physical
Android smoke is interrupted by foreground app switching, treat it as invalid
evidence; the helper reports `mCurrentFocus` and `mFocusedApp` to make that
environment failure explicit.

## Not V1

V1 does not need:

- a full app-wide TypeScript rewrite
- React Native UI conversion
- Electron renderer conversion
- generated API clients
- runtime schema libraries unless plain TypeScript plus validation helpers becomes too weak
