# Kepos Cross-Device Smoke Recipe

This is the project-level recipe for agents validating Kepos across desktop and Android.
It complements `docs/v1.20-smoke-guide.md`, which is the manual user checklist.

## Purpose

Use this recipe before calling V1 or a cross-device change ready.

The goal is not to click every screen. The goal is to prove the product path:

- desktop and Android can start
- identities persist
- trust can be created
- trusted home join works
- room chat stays in the room
- Treehole sync respects owner/trust rules
- Chat setup and body traffic stay separate from room chat
- durable Chat messages survive restart
- revoke blocks future access

## Gates

Run the strongest practical gate first:

```sh
npm run v1:gate
```

Use a fresh APK gate when native Android output changed:

```sh
npm run android:assemble
```

Use a standalone release APK when proving the installed-app path:

```sh
npm run android:install:release
```

When producing release proof, run the CLI smoke set after the gate:

```sh
npm run smoke:desktop
npm run smoke:desktop:pear
npm run smoke:desktop:contacts
npm run smoke:desktop:contacts:pear
npm run smoke:android
npm run smoke:two-device:debug
npm run smoke:two-device:debug:pear
```

`smoke:desktop` is the normal desktop proof. `smoke:desktop:pear` and
`smoke:desktop:contacts:pear` are explicit Pear/Bare bridge checks that set
`KEPOS_DESKTOP_PEAR=1`. Keep them for bridge-sensitive changes, but do not treat them as the default
desktop product path or final V1 release proof.

`smoke:two-device:debug` is allowed to use debug import paths because it targets live transport,
storage, restart, and revoke without depending on camera focus or long Android text input.
It should be run on a connected physical Android device when emulator networking or dev-client
startup is unstable. The current script passes the desktop direct TCP endpoint into Android when the
desktop exposes one, then verifies bidirectional room chat, Treehole state fallback, the same
Treehole post appearing in Android trusted profile Recent posts, signed message body exchange,
Android Chat restart persistence, post-restart Chat delivery, and revoke.
This is live runtime proof, not the normal release proof. It deliberately bypasses the product
entry path where one user scans the other user's Profile QR, sends a friend request, the other user
ignores it, allows new requests, accepts the second request, and both users continue through
Chat, trusted profile, explicit Home entry, Treehole, restart, and revoke.
The script now explicitly brings the Kepos dev client to the foreground before Android UI subflows
and fails with `mCurrentFocus`/`mFocusedApp` details if the physical phone is switched to another app
while a text wait is running.
`smoke:two-device:debug:pear` runs the same debug cross-device product path while the desktop side
uses the bundled Pear/Bare worker instead of the deterministic in-process fallback.
It is an opt-in worker bridge check on the live two-device runtime, and it still does not replace
the physical QR and normal friend-request release proof.

Do not treat this CLI smoke set as the default check after every code change.
For ordinary implementation work, use focused tests plus `npm test` and
`npm run lint`. Run physical or cross-device smoke only when explicitly asked,
when the change cannot be proved another way, or when producing the final V1
release proof packet.

## Final V1 Release Proof Packet

Do this once before calling V1 ready. It is intentionally not part of
`npm run v1:gate`, because it needs a real desktop screen, a real Android
camera, two app lifecycles, and a human observing the normal product path.
The debug and physical QR helpers are sub-proofs; they do not replace this
normal product path.

Record this packet in the release note or PR comment:

- commit SHA and branch
- worktree state: clean, dirty-local, or unknown
- `npm run v1:gate` result
- desktop mode: normal Electron; optionally record Pear/Bare worker if that opt-in check was run
- Android device model and `ANDROID_SERIAL`
- whether Metro/dev-client or installed APK was used
- whether physical Profile QR scan passed
- optional: whether Advanced Home QR scan passed as a transport-descriptor check
- observed Home peer count when the desktop receives the friend request
- observed Home peer count when accept/invite return completes
- Home peer count evidence source: desktop `#peerLabel`; Android
  `room-transport-debug` after Advanced is opened; screenshot or log path
- screenshots or logs for any failed step

Generate a markdown packet before the manual run with:

```sh
npm run v1:proof:packet -- --output tmp/final-v1-proof.md
```

This helper is intentionally non-invasive. It only fills best-effort branch,
commit, worktree state, and Android metadata, then prints the checklist below. It does not
launch apps, run smoke, reset storage, or touch device state. Omit `--output`
to print the same packet to stdout.

Evidence boundaries to keep explicit in the packet:

- `npm run v1:gate` proves source, bundles, export, and non-device model
  behavior for the recorded commit and worktree state; it is not final release proof by itself.
- Desktop self-run smoke proves the normal desktop app path; optional Pear smoke checks the bridge. They do not
  prove Android camera, Android persistence, or cross-device trust UX.
- Android self-run smoke proves local Android create/open/post/restart behavior;
  it does not prove desktop-to-Android friend request and Chat flow.
- Debug two-device smoke proves live transport and persistence sub-paths; it
  does not replace the normal Profile QR -> request -> ignore -> allow -> request -> accept release path.
- Profile-level request delivery must be proved with Home peer count allowed to
  stay at zero through request receipt and accept. Record the observed Home
  peer count at request receipt and accept/invite return. Use desktop
  `#peerLabel` and Android `room-transport-debug` after opening Advanced when
  available. Enter Home is a separate post-trust step.
- V1 ready requires one recorded normal cross-device run where every
  product-path checklist item below is checked.

Before starting the manual run, check:

- `npm run v1:gate` passed on the same commit and worktree state being proved.
- Worktree state is recorded; commit first or explicitly mark the proof as
  dirty-local evidence.
- Desktop runtime choice is recorded before starting the run.
- Android runtime choice and device serial are recorded before starting the run.
- Android screen is unlocked and focused on Kepos before QR steps.
- Old smoke data is either intentionally kept for persistence proof or cleaned
  with `npm run storage:cleanup`.

Run the proof in this order:

1. Start desktop and Android from clean enough state.
2. Desktop shows My QR from Start or Contacts without entering Home.
3. Android scans the desktop Profile QR through the camera.
4. Android sends a friend request from the scanned profile target.
5. Android shows the request as Request pending before acceptance.
6. Desktop receives the incoming request through profile-level delivery while
   Home peer count may be zero.
7. Restart Android before desktop handles that request.
8. Android still shows the outgoing request as Request pending after restart.
9. Desktop ignores the friend request.
10. Desktop shows Android in Removed / ignored and chooses Allow requests.
11. Android sends the friend request again.
12. Desktop accepts the second friend request.
13. Both sides show the other side in Contacts.
14. Both sides open the trusted profile detail and see Message as the primary enabled action.
15. Android opens Chat, selects the desktop contact, opens the same profile detail
    from the Chat row or current-thread header, then sends a message.
16. Desktop replies from the same durable Chat thread and can open the same
    profile detail from the Chat row.
17. Restart both apps.
18. Both sides still show the trusted contact and the prior Chat thread.
19. Desktop creates or reopens its Home.
20. Android opens the desktop contact profile and explicitly chooses Enter Home.
21. Android reaches the desktop Home without typing a raw Home key.
22. Desktop creates a Treehole post.
23. Android refreshes or opens the desktop profile Recent posts and sees that post.
24. Desktop revokes Android from Contacts.
25. Android can no longer use that trust relationship for future Home/Chat access.

Passing means all of these are true:

- trust starts from Profile QR plus friend request, not Home QR
- request receipt and accept do not require Home peer membership
- outgoing friend requests survive restart, ignored requests stay visible, and
  Allow requests permits a new request without restoring trust
- Home entry is explicit from a trusted profile
- Chat rows and Contacts rows open the same trusted profile detail, with
  Message as the primary post-accept action
- Chat messages are durable across restart
- room chat, Chat, and Treehole posts stay separate
- Recent posts load from the trusted profile's Home/Treehole path
- revoke removes future access but does not promise to delete already copied data

If a step fails, do not mark V1 ready. Keep the failed packet and turn the
failure into a fix, a tighter automated test, or an explicit V1 limitation.

## Manual Physical QR Check

Use the helper when possible:

```sh
npm run smoke:physical-qr
npm run smoke:physical-qr:pear
```

The helper stages the desktop QR dialog and Android scanner for each step, then waits for real
screen-to-camera scan results. It still needs a human to aim the phone at the desktop screen.

Run this when QR rendering, scanner UI, camera permissions, layout, or release confidence changed:

1. Start desktop and Android.
2. Desktop creates a home.
3. Desktop opens Large Profile QR.
4. Android scans it and creates trust.
5. Desktop trusts Android through URI import or scan.
6. Desktop opens Large Home QR.
7. Android scans it and joins the trusted-only home.

Expected:

- Android shows a real camera preview before scanning.
- No raw 32-byte room key is needed.
- Profile QR creates trust.
- Home QR joins only after trust exists.
- The scanner can be cancelled without breaking lobby state.

For final V1 release proof, pair this physical QR sub-proof with the normal cross-device product
path: Profile QR scan, friend request, ignored request recovery, second request acceptance,
Chat exchange, explicit trusted Home entry, remote Recent posts refresh, restart persistence
on both sides, and revoke blocking future access.

## Persistence Checks

Always include restart evidence when touching identity, contacts, home state, Chat threads, or storage:

- desktop contact remains after desktop restart
- message request rows remain after app restart
- Android identity remains after app restart
- Chat thread metadata remains after restart
- prior Chat messages remain in the thread after restart
- a new Message can still be sent after restart

If a smoke uses a temporary desktop `userDataDir`, contacts are expected to disappear after that
smoke exits. Do not confuse that with normal desktop profile persistence.

## Isolation Checks

Verify these flows do not leak into each other:

- room chat messages do not appear in Chat panes
- Chat bodies do not appear in room chat
- Treehole posts are not treated as room messages
- public home access does not grant Treehole read
- trust grants Treehole access and Chat eligibility

## Revoke Checks

For revoke-sensitive changes, verify:

- revoked contacts leave trusted contact lists
- revoked contacts leave Chat recipient options
- accepted Chat receive paths are closed for future traffic
- previously replicated data is not promised to disappear

## Device State Checks

Before blaming Kepos UI, check device state:

```sh
adb shell dumpsys power | rg 'mWakefulness|mState='
adb shell dumpsys window | rg 'mCurrentFocus|mFocusedApp'
adb shell pidof io.guion.kepos
```

Locked Android screens, notification shade, or missing Metro should be treated as test environment
state until proven otherwise.
If `mCurrentFocus` or `mFocusedApp` names another package while a smoke is waiting for Kepos UI,
that run is invalid environment evidence, not product evidence. Re-run with the phone left idle and
unlocked.

## Cleanup

Before reporting completion, stop dev servers and app processes started only for smoke, then check:

```sh
pgrep -fl 'expo start|mobile:start|Electron.app|smoke-two-device|smoke-android|maestro test' || true
```

Use the storage cleanup tool for leftover smoke data. It is dry-run by default:

```sh
npm run storage:cleanup -- --desktop-smoke-tmp
npm run storage:cleanup -- --android-app-data
```

Desktop smoke cleanup requires both a known Kepos smoke temp prefix and the
`.kepos-smoke-storage` marker written by the smoke script. This keeps
disposable smoke storage separate from normal desktop user data.

Only apply destructive cleanup with the confirmation flag:

```sh
npm run storage:cleanup -- --desktop-smoke-tmp --apply --i-understand-this-deletes-kepos-data
ANDROID_SERIAL=<device-id> npm run storage:cleanup -- --android-app-data --apply --i-understand-this-deletes-kepos-data
```

For desktop app-data reset, pass the Electron `userData` path explicitly:

```sh
npm run storage:cleanup -- --desktop-user-data-path "$HOME/Library/Application Support/Kepos"
```

The final report should name which gates and smoke paths passed, and whether physical QR was run by
the agent or by the user.

When `smoke:two-device:debug` fails while revealing Android controls or reading the Android Profile
URI, inspect the printed Android screenshot and UI XML paths first. Those files distinguish real
connection failures from the script repeatedly scrolling because an expected control is not visible,
not expanded, or not yet rendered.
