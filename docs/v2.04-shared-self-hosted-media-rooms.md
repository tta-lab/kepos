# V2 Shared Self-Hosted Media Rooms

This document records a V2 product direction: Kepos turns mature
self-hosted media services into trusted shared rooms.

The short version:

```text
Kepos does not become the media platform.
Kepos makes self-hosted media usable as a private shared space.
```

## Product Thesis

Many people already run good self-hosted media services:

- Navidrome and other Subsonic-compatible music servers
- Jellyfin, Plex, and Emby for video
- Audiobookshelf, Kavita, and Calibre-Web for reading and audiobooks
- Immich, file browsers, and simple HTTP servers for media libraries

These products are strong at media ownership, scanning, metadata, playback, and
library management. Kepos should not rebuild that work.

Kepos should add the missing social layer:

```text
identity + trust + invite + shared room state + local P2P proxy + revoke
```

The product-level action is:

```text
Share this self-hosted media space with these trusted people, here, for now.
```

This lets people who can self-host cooperate with people who understand music,
films, books, or other media, without requiring a public server, a platform
account, or a VPN.

## Boundary

Kepos owns:

- trusted room membership
- signed invites
- presence
- shared queue and control state
- local P2P access to the owner's self-hosted service
- revoke, expiry, and visible stop controls
- adapter state for the current media room

The self-hosted product owns:

- media files
- library scanning
- metadata
- playlists and collections
- transcoding when the product already supports it
- subtitles, covers, chapters, and format-specific behavior
- long-term media user data

Kepos should not become:

- a music server
- a video server
- an ebook server
- a metadata scraper
- a transcoder
- a public media hosting platform
- a full NAS permission system

## First Product Shape

The first shared media room should use the local service tunnel as its access
path and keep room control state in Kepos.

For a music room:

```text
Neil Navidrome or HTTP music service
  -> Neil Kepos local proxy owner side
  -> Kepos P2P tunnel
  -> Ada Kepos local proxy
  -> Ada browser audio player
```

Room state flows through Kepos control messages, not through the HTTP proxy:

```text
queue.add
queue.move
queue.remove
playback.play
playback.pause
playback.seek
playback.skip
```

The HTTP or TCP proxy only moves media bytes and related media assets.

## Music Room V1

The first useful version should target a shared listening room, not recording,
karaoke, or a full music platform.

Requirements:

- the owner's music lives in a NAS or self-hosted HTTP music service
- the room has one shared queue
- the room has one current track
- every authorized room member can add songs and control playback by default
- every listener hears the same track
- new joiners seek to the current track position
- normal network conditions should usually stay within about 500 ms
- recording requests are out of scope and can live in an external table

The room state can use a shared clock model:

```ts
type MusicRoomState = {
  roomId: string
  hostProfileId: string
  queue: MusicTrack[]
  currentTrackId: string | null
  playback: {
    status: 'playing' | 'paused'
    trackStartedAtRoomTime: number
    positionMsAtStartedAt: number
    version: number
  }
  controllerProfileIds: string[]
}
```

Each client computes the target local playback position:

```text
targetPosition =
  positionMsAtStartedAt + (nowRoomTime - trackStartedAtRoomTime)
```

Suggested correction policy:

- ignore drift below 150 ms
- use slight playback-rate correction for medium drift
- seek for large drift, such as more than 800 ms
- discard stale playback events by `version`

This is not sample-accurate sync. It is good enough for a shared listening room
where everyone should hear the same song at roughly the same time.

## Adapter Direction

The preferred first adapter is a Subsonic-compatible music service, such as
Navidrome.

Reasons:

- music has a simple queue model
- tracks are shorter than films
- users tolerate small sync drift
- Subsonic-compatible APIs are mature
- Kepos can use track identity, artwork, and stream URLs without scanning files

Other adapters should follow only after the first music room proves the model.

Likely sequence:

1. Music room

   Start with Navidrome or another Subsonic-compatible server.

2. Audiobook or reading room

   Audiobookshelf is close to music for audio. Ebook co-reading is different:
   the shared state is chapter, page, selection, and notes rather than audio
   playback.

3. Watch room

   Jellyfin, Plex, or Emby can support shared film watching later, but video
   adds more hard problems: long buffers, subtitles, transcoding, device
   compatibility, and seek recovery.

Future adapters may include drawing, creative tools, local AI tools, and other
self-hosted software. They should reuse the same room and tunnel primitives.

## Relationship To Local Service Tunnel

The local service tunnel is the infrastructure primitive.

Shared self-hosted media rooms are product wrappers over that primitive:

```text
Shared App Infrastructure
  - trust authorization
  - session lifecycle
  - local P2P proxy
  - invite, revoke, and expiry
  - presence
  - shared control events

Domain Adapter
  - music
  - film
  - audiobook
  - reading
```

Raw local port sharing can exist as an advanced mode, but the main user
experience should be adapter-led. A normal user should see "start music room"
or "watch together", not "forward port 4533".

## NAS And LAN Services

Many owners will keep media on a NAS.

The owner may expose the NAS through a local HTTP service:

```text
Navidrome on 192.168.1.10:4533
Jellyfin on 192.168.1.10:8096
nginx static music directory on 127.0.0.1:8080
```

Kepos may eventually support explicit LAN targets, but this must be visible and
narrow:

```text
Share NAS service 192.168.1.10:4533 with Ada for this room.
```

It must not silently become broader LAN access. A share grants access to one
explicit service, for one signed room, for allowed peers, until it is closed,
revoked, or expired.

## Non-Goals

The first shared media room should not include:

- recording requests
- karaoke or live singing
- shared microphone capture
- Kepos-owned media upload
- public catalogs
- public discovery
- public watch parties
- generic NAS browsing
- arbitrary LAN routing
- Kepos-owned transcoding

Recording requests can remain an external table until the listening room itself
is proven. Later, a request item can point to a finished media item in the
self-hosted library.

## Success Bar

The first shared music room is real when:

- Neil's music lives in a NAS-backed or self-hosted HTTP music service.
- Neil starts a Kepos music room from his trusted home.
- Ada joins the room through Kepos trust.
- Ada can add a song to the queue.
- Neil and Ada hear the same track.
- Ada pauses and both clients pause.
- Neil skips and both clients move to the next track.
- A new listener joins and seeks to the current track position.
- Neil can close the room and the local service share closes with it.

This gives Kepos a clear V2 path: use mature self-hosted products for media
complexity, and provide the trusted shared-space layer they do not provide.
