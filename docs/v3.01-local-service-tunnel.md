# Future Local Service Tunnel

This document records a future Kepos architecture primitive: a trusted,
session-scoped local service tunnel.

The short version:

```text
Kepos port-forward for trusted friends.
```

## Idea

Kepos can let a trusted peer access one explicit local service without exposing
that service to the public internet.

The owner shares a local TCP service:

```text
Neil machine:
  127.0.0.1:3000
```

The guest gets a local proxy:

```text
Ada machine:
  127.0.0.1:8123
```

Traffic flows through Kepos:

```text
Ada app/browser
  -> 127.0.0.1:<guest-proxy-port>
  -> Ada Kepos
  -> Kepos P2P tunnel
  -> Neil Kepos
  -> 127.0.0.1:<owner-service-port>
  -> Neil local service
```

This is similar in shape to `kubectl port-forward`:

```text
kubectl port-forward:
  localhost -> Kubernetes API server -> Pod

Kepos local service tunnel:
  localhost -> trusted Kepos P2P session -> friend's localhost service
```

## Why This Matters

This turns Kepos trust into temporary private reachability.

It gives existing local software a way to live inside a trusted home without
requiring:

- public IP addresses
- manual port forwarding
- DDNS
- public DNS
- a central web server
- a full VPN

The product-level action is not "configure networking." It is:

```text
Share this local app with Ada.
```

The individual techniques are not new. Port forwarding, SSH tunnels, VPNs,
P2P transports, and local web apps all exist.

The product bet is the combination:

```text
identity + trust + home + signed session + P2P tunnel + revoke
```

That combination turns local software into a social object. A home can become a
place where trusted friends temporarily use one of the owner's local services
without the owner publishing that service to the internet.

This is different from developer tunnels and VPNs:

- developer tunnels expose a service through a URL or relay, usually outside a
  persistent social trust model
- VPNs expose a broader private network, usually outside a product-level home
  and invite model
- Kepos should expose one explicit service to one explicit trusted peer or home
  session

As of this planning note, the most interesting opportunity is not inventing a
new tunnel. It is making this narrow tunnel feel like a natural part of a
private home.

The broader product thesis is a private P2P shared space for a trusted circle.
Kepos is not trying to be a generic developer tunnel, a public hosting platform,
or a VPN control panel. It is trying to let friends share things that normally
stay local without handing ownership of the space to a platform.

That social framing is the differentiator:

```text
not "publish this service"
but "share this with these trusted people, here, for now"
```

## Relationship To V3 RetroArch

The V3 RetroArch plan is one specialization of this primitive.

RetroArch expects a TCP host/port for netplay. Kepos can provide that host/port
locally:

```text
Ada RetroArch
  -> Ada localhost proxy
  -> Kepos P2P tunnel
  -> Neil localhost RetroArch netplay port
  -> Neil RetroArch
```

So V3 should be understood as:

```text
RetroArch adapter + Local Service Tunnel
```

RetroArch still owns emulation and netplay. Kepos owns the trusted tunnel and
session lifecycle.

## Relationship To Shared Self-Hosted Media

Shared self-hosted media rooms are another specialization of this primitive,
even if the product work lands in V2 before V3 game sessions.

The product bet is:

```text
Kepos does not become the media platform.
Kepos makes self-hosted media usable as a private shared space.
```

For example, a music room may use a NAS-backed Navidrome or
Subsonic-compatible service as the media source:

```text
Ada browser audio player
  -> Ada localhost proxy
  -> Kepos P2P tunnel
  -> Neil Kepos
  -> Neil Navidrome or HTTP music service
  -> Neil NAS
```

Kepos owns trusted room membership, shared queue state, playback control, local
P2P access, revoke, and expiry. The self-hosted product owns media files,
library scanning, metadata, transcoding if available, covers, subtitles,
chapters, and format-specific playback behavior.

This keeps Kepos from becoming a music server, video server, ebook server,
transcoder, or NAS permission system. Kepos supplies the shared-space layer for
trusted people.

## Other Possible Uses

The same primitive could support:

- sharing a local web demo
- opening a friend's local dev server
- sharing Jupyter Notebook
- sharing a local AI UI such as Ollama, ComfyUI, or Stable Diffusion WebUI
- temporary access to a file browser
- temporary access to a self-hosted photo gallery
- old game servers that use a single TCP port
- internal admin pages for a trusted helper

Each use should be an explicit share, not a general network bridge.

## Non-Goals

This is not a VPN.

Kepos should not expose:

- a virtual network interface
- arbitrary LAN routing
- all local ports
- DNS rewriting
- transparent system-wide traffic capture
- permanent machine access

This is also not a public tunnel service like ngrok. The intended audience is a
trusted peer or small trusted home, not the open internet.

## Security Rules

This primitive is powerful and must be narrow by default.

Rules:

- every tunnel is created by an explicit signed share
- every tunnel is scoped to one local host and one local port
- every tunnel has an allowed peer list
- every tunnel is visible while active
- every tunnel can be closed immediately by the owner
- every tunnel expires by default
- revoked contacts cannot open new tunnels
- existing tunnels close when a relevant revoke is applied
- tunnels never grant access to other local ports
- tunnels do not imply broader home, treehole, or DM permission

The owner should see something like:

```text
Sharing localhost:3000 with Ada
```

The guest should see something like:

```text
Open Neil's shared app at localhost:8123
```

## Domain Shape

```ts
type LocalServiceTunnel = {
  type: 'kepos.local-service-tunnel.v1'
  version: 1
  tunnelId: string
  ownerProfileId: string
  allowedProfileIds: string[]
  label: string
  protocol: 'tcp'
  ownerHost: '127.0.0.1'
  ownerPort: number
  guestHost: '127.0.0.1'
  guestPort?: number
  sessionDiscoveryKey: string
  createdAt: number
  expiresAt: number
  proof: unknown
}
```

Rules:

- `proof` must verify against `ownerProfileId`.
- `ownerHost` is `127.0.0.1` for the first version.
- `guestPort` may be selected by the guest if the requested port is busy.
- `sessionDiscoveryKey` is a tunnel capability, not identity or trust.
- `allowedProfileIds` is checked against current local trust/revoke state before
  opening.

## Transport Shape

The first version should forward one TCP stream:

```text
local TCP socket <-> Kepos framed stream <-> remote TCP socket
```

Kepos does not need to parse the inner protocol. It only needs:

- open
- close
- bytes from guest to owner
- bytes from owner to guest
- error
- metrics

Minimal frame types:

```ts
type TunnelFrame =
  | {
      type: 'kepos.tunnel.open.v1'
      tunnelId: string
      streamId: string
    }
  | {
      type: 'kepos.tunnel.data.v1'
      tunnelId: string
      streamId: string
      sequence: number
      bytes: Uint8Array
    }
  | {
      type: 'kepos.tunnel.close.v1'
      tunnelId: string
      streamId: string
      reason?: string
    }
```

## Product Boundary

Kepos should expose product-specific wrappers before exposing a raw tunnel UI to
everyone.

Good first wrappers:

- shared self-hosted music room
- shared audiobook or reading room
- shared film room
- RetroArch game session
- share local web app
- share local AI tool
- share local notebook

Raw local port sharing can remain an advanced or developer feature until the
security UI is clear.

## Implementation Order

1. Local-only proxy probe

   Forward `127.0.0.1:A` to `127.0.0.1:B` on one machine to prove socket
   lifecycle and byte forwarding.

2. Two-process Kepos tunnel probe

   Run owner and guest Kepos locally, forward through the Kepos stream layer,
   and test with a simple HTTP server.

3. Cross-device P2P tunnel probe

   Forward a simple HTTP server between two machines over Kepos P2P.

4. RetroArch probe

   Put RetroArch netplay through the tunnel.

5. Product wrapper

   Add signed shares, UI state, expiry, revoke close, and per-feature labels.

## Success Bar

The primitive is real when:

- Neil shares `127.0.0.1:3000` with Ada.
- Ada gets a local port from Kepos.
- Ada opens the local port in a browser.
- The page comes from Neil's local service.
- Neil can see and close the share.
- The share closes automatically on expiry or revoke.

After that, RetroArch game sessions become a specific adapter instead of a
one-off network trick.
