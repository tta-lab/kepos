# V1 Final MLP UI/UX Refactor

This document closes the V1 MLP product model after the UI polish and QR/trust
discussion.

The key change is that Kepos should stop presenting Home, Profile QR, direct
channels, and treehole replication as separate protocol tools. V1 should
present a person-first social model:

```text
person -> profile -> trust -> Home / Recent posts / Chat
```

Internal rooms, keys, QR payloads, and replication channels still exist. They
should not define the normal product path.

## Decision

V1 should use one main social path:

```text
scan a person
send a friend request
accept the request
mutual trust is established
open the contact profile
message them, read recent posts, or enter their home
```

There should be no normal Home QR path in V1 MLP.

Home is not a separate thing users invite people into. Home is the default space
behind a trusted profile.

## Final Product Model

### Profile

Profile is the user's identity and public social entry point.

It owns:

- display name and avatar
- profile id and signing key
- one home
- one treehole
- one direct-message relationship per trusted contact
- trust and revoke controls

Normal users should scan a profile, not a room.

### Trust

Trust is a relationship between two profiles.

V1 trust is created by a two-sided flow:

1. A scans B.
2. A sends a friend request.
3. B accepts.
4. A trusts B.
5. B trusts A.

From the bottom up, this is still two local trust grants:

```text
A contact book: B is trusted
B contact book: A is trusted
```

The product should show this as one friend relationship.

Revoke is one-sided:

```text
A removes B
```

After that, B can no longer enter A's home or receive new A-owned treehole
bootstrap data. B may still have old replicated data locally. V1 should not
claim remote erasure.

### Home

Home is a live space owned by a profile.

Trust enables access. It does not imply automatic presence.

Users enter a home by opening a trusted contact's profile and choosing
`Enter Home`.

Scanning, accepting, or trusting must not auto-join a room. This keeps the
relationship action separate from the presence action.

### Treehole / Recent posts

Treehole is durable profile content.

Treehole still has a first-class V1 role: it is where I post my own updates.
This is not a generic feed and not a room chat replacement.

For my own profile, Treehole is the composer and history for my durable posts.
For another trusted contact, their profile shows recent treehole posts as
`Recent posts`. This can be implemented as a simple pull/read when the profile
is opened. V2 can turn it into a live feed stream.

Rules:

- owner creates main posts
- trusted contacts can read, comment, and like
- untrusted or pending contacts cannot read private treehole content
- public home access, if kept for debug, does not imply treehole read

### Chat

Chat should feel like QQ or WeChat.

There should be a Chat surface with a thread list:

- one row per active message thread
- avatar/name
- last message preview
- last message time
- unread badge when a read marker exists
- failed/pending state later

Opening a row enters the durable pairwise chat thread.

The profile page can also have a `Message` action, but it opens the same thread.
There must not be two different DM concepts depending on where the user starts.

### Contacts

Contacts manage relationships.

Contacts should list trusted people and pending requests. Opening a contact
shows the profile page.

Contacts is not the primary DM inbox. It is the address book and trust surface.

## Target Information Architecture

V1 should converge to:

```text
Home
Chat
Contacts
Treehole
```

Profile is a detail page opened from Contacts, Chat, or search/scan results.

Treehole should stay in V1 as the user's own posting surface. It should not be
presented as a generic feed or as a separate protocol console.

Other people's treehole content should be read through their profile:

```text
Contact profile
  -> recent posts
  -> Message
  -> Enter Home
  -> trust controls
  -> identity details
```

The final V1 MLP should make clear whose treehole is being shown:

- `Treehole`: my own durable posts and composer
- `Recent posts`: a trusted contact's durable posts on their profile

## Implementation Checkpoint

This pass lands the first concrete version of the model without pretending the
whole target exists.

Implemented:

- ContactBook now tracks outgoing friend requests separately from trusted and
  incoming pending requests.
- Desktop and Android Contacts now show outgoing friend requests as `Sent
requests`, so sending a profile request no longer feels like it disappeared
  before acceptance.
- Desktop and Android incoming request panels now use `Friend requests` product
  copy; protocol-level message-request wording stays in code and tests, not in
  the normal Contacts UI.
- Desktop and Android request action accessibility labels now also use friend
  request wording, so screen-reader users hear the same product model as sighted
  users.
- Contacts navigation badges now count both incoming friend requests and
  outgoing sent requests.
- Accepting a request-bound DM invite completes the requester side of mutual
  trust and clears the outgoing request.
- Desktop and Android normal navigation now uses `Chat` and `Contacts` as
  product labels while keeping internal `dm` and `people` ids stable.
- Desktop and mobile React component files were migrated from JSX to TSX.
  `mobile/App.tsx` is now the checked runtime composition entry, while mobile
  rendering has been split into typed TSX component slices for setup, lobby,
  room, messages, treehole, contacts, requests, tabs, chrome, and forms.
- Contacts now opens a real per-contact profile detail on desktop and Android.
  The detail surface shows a stable avatar placeholder, short profile
  fingerprint, trust state, `Message`, `Enter home`, `Recent posts`, remove
  friend, and advanced identity details.
- Desktop and Android contact rows now share the same contact profile view-model
  for display name, trust labels, action labels, Home entry availability, and
  Recent posts copy.
- `Message` from a contact profile opens the same durable pairwise message
  surface by selecting that profile as the recipient.
- Android and desktop Chat can show accepted thread rows from persisted DM
  thread state, including contact label, latest-message preview, time label,
  accepted-thread state, and latest-activity ordering. Selecting a row switches
  the active recipient.
- Desktop and Android Chat can also keep requested thread rows visible as
  `Request pending`, so a sent request does not disappear from the inbox while
  waiting for acceptance.
- Desktop and Android incoming requested thread rows now expose Accept and
  Ignore actions directly in Chat; outgoing pending rows remain passive
  waiting rows.
- The shared Chat thread row model now accepts explicit per-contact read
  markers and computes unread incoming counts from them. Desktop and Android
  thread rows can render the resulting unread badge without inventing unread
  state when no read marker exists. Thread selection now stores local read
  markers in the persisted DM thread state.
- Desktop and Android empty thread lists now link back to Contacts with scan or
  request-acceptance guidance, instead of silently showing no inbox.
- Desktop Chat thread rows can open the same trusted contact profile detail
  in Contacts. Android Chat thread rows can also open the same profile
  detail.
- Android Profile QR scans inside an active home now verify the signed profile
  QR as a friend-request target, select that profile in Chat, and show a
  small request preview before the user sends the request message.
- Android profile-scan request previews can open a limited profile detail for
  the scanned request target before trust exists.
- Desktop Profile QR paste now verifies the signed profile QR as a friend-request
  target, selects that profile in Chat, shows a request-target preview card,
  and can open the same limited profile detail before trust exists.
- Desktop and Android request-target previews now share a relationship-state
  view-model, so outgoing, incoming, ignored, revoked, and already-trusted
  targets show explicit copy and duplicate request sends are blocked.
- Android Profile QR scan and paste now select a friend-request target instead
  of directly trusting the scanned profile in the normal UI. The direct-trust
  helper is kept only as explicitly named debug/support code.
- Desktop and Android `Enter home` can now use a saved signed Home descriptor
  for a trusted contact. Scanning/pasting a signed Home QR stores that
  descriptor only when the owner is already trusted; it does not create trust.
- Desktop and Android trusted contact profiles now show real `Recent posts`
  when the selected profile owns the currently joined Home and that Home's
  Treehole posts are loaded. They also keep a same-run per-profile cache after
  non-empty Treehole posts are seen, so leaving a Home does not immediately
  empty that profile detail. This is intentionally not a global feed yet.
- Desktop and Android now share a deterministic generated profile avatar model.
  Contacts, trusted profile detail, Chat thread rows, and direct message
  bubbles, and Treehole author rows show stable initials/color placeholders even
  before real avatar sync exists.
- Desktop and Android Chat now show a current-thread header when an accepted
  thread is selected, and the composer placeholder names that thread instead of
  presenting the normal path as a manual recipient entry.
- Desktop Chat accessibility copy now uses `Chat` and friend-request
  wording instead of the old direct-message request language.
- Desktop Contacts copy now points users to `Chat` and message threads
  instead of leaking the older direct-message product wording in normal empty
  states.
- `Treehole` is framed as my own durable posting surface; contact profiles show `Recent posts`
  as the place where another profile's durable content will appear.
- Signed profile QR parsing now has a pure "request target" path that verifies
  the QR without mutating trust state. The old direct trust scan remains as an
  advanced/debug path.
- Desktop and Android now keep a durable per-profile Recent posts cache and
  keep Recent posts as read-only profile context. Enter Home remains the only
  profile action that enters a contact's Home; there is no hidden Refresh posts
  shortcut into Home.
- Android quick-start now uses `Show My QR` and `Open Contacts` as normal
  social actions. Home QR show/scan remains available in Advanced transport
  controls and physical QR smoke, but the first-run panel no longer teaches Home
  QR as the sharing path.
- Desktop normal Home context now also exposes `Show My QR` beside `Open my
home`, so the primary desktop path matches the product rule that profile QR is
  the social entry point. Raw Profile QR details remain Advanced.
- Desktop and Android remaining visible setup labels now say `Contacts` rather
  than `People`. The internal component/route names can stay stable while the
  product language presents an address book.

Still intentionally not claimed:

- Avatar import and first-pass verified Home-control avatar byte sync exist on
  desktop and Android. V1 still does not claim a full profile-feed protocol,
  multi-device profile sync, or remote avatar deletion semantics; generated
  placeholders remain the fallback when no verified local avatar media exists.
- Desktop preload/main/worker paths now publish DM thread snapshots through
  `dmThreadChanged`, and Pear desktop smoke covers the same worker-backed
  inbox/request persistence path for the current source shape. Final release
  proof should rerun that path, but this is no longer an unproven source-level
  Chat gap.
- Final cross-device proof is still pending for descriptor refresh, explicit
  contact Home entry, and trusted Recent posts profile context on real devices.
- No automatic home entry from scan, accept, or trust.
- No Android device smoke was run for this checkpoint unless explicitly
  requested; low-cost source, unit, type, lint, and bundle gates are the default.

## Main UX Flows

### Add A Friend

```text
Contacts -> Scan
scan profile QR
preview person
Send request
recipient sees incoming request
recipient accepts
both sides become trusted contacts
```

The scan result should show a profile preview before sending:

- name/avatar if present
- short fingerprint
- clear target action: `Send request`

The normal UI should not ask the user to choose between Profile QR and Home QR.

### Open A Contact Profile

```text
Contacts -> contact row -> Profile
```

Trusted profile actions:

- Message
- Enter Home
- Recent posts
- Remove friend
- Advanced identity details

The visible action and success notice should use product language:
`Remove friend` and `Friend removed.` Keep `revoke` for the internal trust
model, tests, and protocol docs.

Pending profile actions:

- Request pending, or Accept / Ignore
- minimal profile info
- no private recent posts
- no Enter Home

Untrusted profile actions:

- Send request
- minimal profile info
- no private recent posts
- no Enter Home

### Enter Home

```text
Profile -> Enter Home
```

Entering Home starts live presence. It is not triggered by scan or accept.

The Home surface should show:

- whose home this is
- live room chat
- online count / peer status
- leave action
- link back to owner profile

Room chat remains ephemeral.

Current source status: desktop and Android now use a shared Home owner
view-model. The Home bar labels `My home`, a trusted contact's Home, or a short
owner fingerprint fallback, and it exposes an owner-profile action when the
owner is a trusted contact.

### Post To Treehole

```text
Treehole -> write post
```

Treehole is the durable place where I post updates for trusted contacts to read.

The Treehole surface should show:

- my recent posts
- a composer for owner posts
- comments and likes from trusted contacts
- clear disabled state if the current view is not my own writable treehole

When viewing someone else, posting should not be available there. Their durable
content belongs on their Profile as `Recent posts`, with trusted comment and
like actions where allowed.

### Send A Message

```text
Chat -> thread
```

or:

```text
Profile -> Message -> thread
```

Both routes open the same durable pairwise thread.

The Chat list should be optimized for resuming chat, not selecting a raw
profile id. Manual recipient entry belongs in Advanced/debug only.

## QR Model

The product should expose one normal QR:

```text
My QR
```

It represents the local profile and starts the friend-request flow.

The QR payload can remain technically close to the existing signed Profile QR,
but the product meaning changes:

```text
signed profile payload -> friend request target
```

The scanner should be one button:

```text
Scan
```

It should auto-detect supported Kepos payloads.

V1 normal behavior:

- profile/friend QR: preview profile, send request
- stale or invalid QR: fail closed with a short error
- home QR: Advanced/debug compatibility only
- message-request QR: Advanced/debug or migration compatibility only

If the implementation temporarily needs both Profile QR and Home QR under the
hood, the UX should still behave as one scan flow. The UI should not ask normal
users to perform two scans.

## Technical Mapping

The target product model can reuse much of the existing architecture:

- local profile remains the identity root
- ContactBook remains trust SSOT
- signed profile QR remains the scanable identity proof
- signed home address remains an internal capability behind trusted profile
  access
- treehole authorization remains owner identity plus ContactBook policy
- DM remains signed/encrypted invite plus durable pairwise thread

The main change is the relationship lifecycle.

Current implemented shape:

```text
Profile QR -> local one-way trust
Home QR -> join attempt
message request -> accepted DM thread
```

Target V1 shape:

```text
Profile QR -> outgoing friend request
accept friend request -> mutual trust
trusted contact profile -> enter home / recent posts / message
```

This means the old one-way trust action should be demoted to Advanced/debug or
replaced by a request/accept action.

## If Technical Merge Is Not Immediate

The UI can still merge first.

Rules:

- show one `My QR`
- show one `Scan`
- show one contact profile page
- hide Home QR and raw Profile QR in Advanced
- make scan results look like people, not payloads
- keep manual home key and manual recipient id in Advanced

Internally, the app may still:

- store profile identity from the signed profile payload
- keep a signed home address for connection
- use existing ContactBook trust records
- use current treehole bootstrap and DM invite plumbing

The important product rule is that the user sees one relationship state across
all surfaces:

```text
untrusted -> request sent / incoming request -> trusted -> removed
```

Home access, recent posts, and direct message availability must read from that
same relationship state.

## Desktop Refactor Target

Current desktop navigation is:

```text
Home / Chat / Treehole / Contacts
```

Target desktop navigation:

```text
Home / Chat / Contacts / Treehole
```

Changes:

- keep Chat as the thread-list surface
- keep Contacts as the address book plus requests surface
- keep Treehole as my own posting surface
- show other people's treehole content as Recent posts on their profile
- keep Advanced identity, home key, and transport detail in collapsible debug
  sections
- keep core rail icons icon-only with accessible labels
- show the active home owner clearly in Home

During migration, keeping the old tabs is acceptable, but the visible copy
should stop teaching users that Home QR and Profile QR are separate tasks.

## Mobile Refactor Target

Mobile should mirror desktop concepts, not desktop layout.

Target mobile tabs:

```text
Home / Chat / Contacts / Treehole
```

Profile should be a pushed/detail screen from Contacts or Chat.

Mobile priorities:

- one-handed scan/add flow
- clear incoming request accept/ignore
- chat thread list with last-message preview
- profile page with Message, Recent, Enter Home
- Treehole as my own post composer/history
- no raw QR or manual key on the first screen
- debug details hidden behind Advanced

## Copy And Naming

Use:

- `My QR`
- `Scan`
- `Friend request`
- `Contacts`
- `Chat`
- `Profile`
- `Home`
- `Treehole`
- `Recent posts`
- `Enter Home`
- `Remove friend`
- `Advanced`

Avoid as primary UI:

- `Profile QR`
- `Home QR`
- `Home invite`
- `room key`
- `profile id`
- `DM`
- `treehole bootstrap`
- `writer grant`
- `Autobase`
- `Hyperswarm`

`Home QR`, manual keys, and transport detail can remain in Advanced, tests,
docs, and debug panels. `Home invite` should not be used as UI copy because it
implies the QR itself grants permission.

`message_request` remains an internal/protocol name for compatibility, but
normal UI should call the user action `Friend request`. Request titles, DM list
metadata, trust-source labels, accessibility labels, and success/error notices
should all use the friend-request model.

## V1 Non-Goals

Do not add these to close V1:

- public room discovery
- guest mode
- temporary invite links
- one-way follow
- group DM
- username registry
- multi-device account sync
- remote deletion claims
- background mobile delivery guarantees
- feed stream subscriptions

These may matter later, but they are not needed for the MLP social loop.

## Implementation Order

1. Define the friend-request state model on top of ContactBook.
2. Change QR scan UX to one profile/friend scan path.
3. Add incoming/outgoing friend request UI.
4. Make accept create mutual trust.
5. Add contact profile view. Done for the Contacts entry point on desktop and
   Android.
6. Move direct messaging into a Chat thread-list model.
7. Keep Treehole as my own posting surface.
8. Put trusted contacts' recent treehole posts on their profile.
9. Make Enter Home an explicit profile action.
10. Demote Home QR, raw Profile QR, manual keys, and manual recipient ids to
    Advanced/debug.
11. Rename or restructure top-level nav after the data model supports the new
    surfaces.

## Success Bar

V1 MLP is done when a new user can explain the app as:

```text
I add trusted friends, open their profile, message them, read their recent
posts, post my own updates, and enter their home when I want to hang out live.
```

It should not require explaining:

```text
First scan a Profile QR, then scan a Home QR, then maybe join a room, then use a
separate Chat panel, then check a separate Treehole tab.
```

That second explanation is a protocol console. The first one is a product.
