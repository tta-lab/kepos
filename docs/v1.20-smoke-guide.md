# Kepos V1 Smoke Guide

This guide is the manual parity check for desktop and Android.

## Build Gates

Run these before device smoke:

```sh
npm run v1:gate
```

`npm run v1:gate` runs lint, tests, TypeScript compatibility probes, desktop bundle generation,
Bare Android bundle checks, Expo Android JS export, and APK native-library alignment checks.

`npm run android:assemble` is the stronger APK build gate when a fresh native build is needed.
Use `npm run android:install:release` when testing the standalone installed APK path instead of
Metro/dev-client.

Current automated coverage proves lint, tests, typecheck, desktop bundle creation, Android bundle
creation, Expo Android JS bundle creation, and APK native-library alignment. Current device smoke
covers Android scanner open/cancel and the debug two-device desktop/Android runtime path when the
Android runtime is stable. Pear/Bare desktop smoke remains an explicit opt-in bridge check, not the
default desktop path or a V1 release gate. The physical QR sub-proof passed for the current desktop
Large Profile QR into Android request-target flow, plus Advanced Large Home QR into trusted-only home
join after trust already exists; it is not the full cross-device V1 release proof by itself.

Desktop Pear/Bare coverage has dedicated opt-in scripts:
`npm run smoke:desktop:pear` and `npm run smoke:desktop:contacts:pear`. They set
`KEPOS_DESKTOP_PEAR=1` and are useful when changing the worker bridge. If they fail while the normal
desktop smokes pass, treat that as a Pear bridge follow-up, not a reason to block ordinary desktop
V1 testing.

`test/v1-model-smoke.test.js` covers the shared V1 model path with one owner and one peer:

- profile QR request target followed by friend request acceptance in both directions
- trusted-only home access after local trust
- treehole writer grant policy from ContactBook
- owner-only treehole posts plus trusted comments and likes
- one message request accepted into a durable DM thread
- signed DM messages persisted through the shared runtime/storage APIs
- revoke blocking future treehole writer grants

This is model evidence only. It does not exercise camera scan permissions, Pear desktop runtime, Android Bare lifecycle, live Hyperswarm transport, or rendered UI state.

`test/qr-rendering.test.js` renders signed profile and home QR payloads and verifies the generated
PNG output can be decoded by `jsQR`. This is no-camera decode evidence; it still does not prove
real screen-to-camera focus, glare, distance, or device camera behavior.

## Basic CLI Smoke

Desktop smoke uses Playwright's Electron support and launches the real Electron app with an isolated
temporary profile:

```sh
npm run smoke:desktop
```

Expected:

- renderer bundle is built before launch
- profile URI starts with `kepos://profile`
- home URI starts with `kepos://home`
- Create Home joins a home
- Home chat send appears in the chat list
- owner Treehole post appears in the Treehole list
- after restart, Profile QR and Home QR remain stable
- after restart, reopening Home restores the owner Treehole post
- treehole state reaches ready

Desktop Pear/Bare smoke is an optional bridge check through `pear-runtime` and the bundled Bare
worker:

```sh
npm run smoke:desktop:pear
```

Expected when the Pear bridge is healthy:

- preload/main connects to the worker through `pear.run()`
- backend-published Profile QR and Home QR reach React
- Create Home joins a home through the worker bridge
- Home chat send appears in the chat list
- owner Treehole post appears in the Treehole list
- after restart, Profile QR and Home QR remain stable
- after restart, reopening Home restores the owner Treehole post
- treehole state reaches ready

Desktop contact persistence smoke launches the real Electron app, trusts a signed profile URI,
restarts with the same temporary `userDataDir`, and verifies the contact is still visible:

```sh
npm run smoke:desktop:contacts
npm run smoke:desktop:contacts:pear
```

Expected:

- profile trust writes to desktop ContactBook storage
- the trusted contact appears in the contact list
- the trusted contact still appears after desktop restart
- a message request can be sent to the persisted trusted contact
- the message request still appears after desktop restart
- revoke removes the trusted contact from the contact list
- the revoked trusted contact stays hidden after restart
- the Pear variant is an opt-in bridge regression check through the bundled Bare worker

Android smoke uses Maestro against the installed standalone Android app. This is intentionally a
basic UI smoke while the mobile UI is still moving:

```sh
npm run smoke:android
```

Install Maestro when needed:

```sh
brew tap mobile-dev-inc/tap
brew install --formula mobile-dev-inc/tap/maestro
```

The `maestro` cask installs the GUI app; the formula installs the CLI used by `npm run
smoke:android`.

Expected:

- lobby exposes stable React Native test IDs
- Scan Profile QR opens a camera scanner and Cancel returns to the lobby
- Advanced Scan Home QR opens a camera scanner and Cancel returns to the lobby
- Create Home opens the room view
- Home and Treehole tabs are visible
- owner Treehole post can be created and appears in the Treehole list
- after app stop/relaunch, reopening Home restores the owner Treehole post

This smoke proves the Android camera scanner UI can open and close. It does not replace periodic
physical screen-to-camera checks for profile/home scans because focus, glare, and device camera
behavior are hardware-dependent.

The manual physical QR sub-proof can be staged with:

```sh
npm run smoke:physical-qr
npm run smoke:physical-qr:pear
```

These scripts launch desktop, create a temporary Home, open the desktop Large Profile QR, open the
Android Profile scanner, then wait while a human points the Android camera at the desktop screen.
After Android reports trust, the script repeats the same flow for the desktop Advanced Large Home QR
and waits for Android to reach the connected Home view. The `:pear` variant uses the bundled desktop
Pear/Bare worker. These are intentionally not part of `npm run v1:gate` because they require a real
screen, a real camera, and human aiming. On timeout, the helper prints desktop and Android
screenshot paths so the report can distinguish app state from camera aim, focus, glare, or lighting.

A debug two-device smoke can exercise the live desktop/Android transport without relying on camera
scan or fragile long-text input through the Android keyboard:

```sh
npm run smoke:two-device:debug
npm run smoke:two-device:debug:pear
```

This launches desktop with Playwright, reads Android's profile URI from the UI hierarchy, writes an
Android app-private ContactBook entry through `adb run-as`, joins the desktop home through the
manual 64-character debug key path, and passes the desktop direct TCP endpoint into Android when the
desktop exposes one. It verifies peer connection, room chat in both directions, desktop-to-Android
treehole state fallback, message request acceptance, signed DM body exchange over the accepted
message thread in both directions, Android Chat persistence across restart, post-restart
Chat delivery, and the desktop revoke path closing the accepted Chat receive path. The `:pear` variant keeps the same
Android/debug setup while the desktop side uses the bundled Pear/Bare worker instead of the
deterministic in-process fallback. It is useful CLI evidence for the live runtime, but physical QR
smoke should still be repeated before release builds.

Final V1 release proof should use the one-run packet in
`docs/v1.21-cross-device-smoke.md`: Profile QR, friend request, ignored request
recovery, second request acceptance, Chat, restart, explicit trusted Home
entry, Recent posts, and revoke. The key friend-bootstrap proof is that Profile
QR request and accept work through profile-level P2P while Home peer count may
be zero. The debug and physical QR helpers are sub-proofs; they do not replace
that normal product path.

The desktop app in this debug smoke uses a temporary Electron `userDataDir`, and the script deletes
that directory when it exits. Contacts created in this smoke are expected to disappear from the
smoke desktop profile and will not appear in a normal manually launched desktop profile.

If a smoke run is interrupted, inspect leftover dev storage with a dry run:

```sh
npm run storage:cleanup -- --desktop-smoke-tmp
```

Desktop smoke cleanup only selects temp directories with a known Kepos smoke
prefix and the `.kepos-smoke-storage` marker written by the smoke script.
Unmarked directories are left alone even if their names look similar.

Apply the cleanup only after checking the printed paths:

```sh
npm run storage:cleanup -- --desktop-smoke-tmp --apply --i-understand-this-deletes-kepos-data
```

For a real desktop app-data reset, pass the Electron `userData` path explicitly. The tool only
removes Kepos-owned subdirectories below that path: `kepos`, `pear-storage`, and `pear-runtime`.

```sh
npm run storage:cleanup -- --desktop-user-data-path "$HOME/Library/Application Support/Kepos"
```

For Android dev data, use a dry run first:

```sh
npm run storage:cleanup -- --android-app-data
```

Then apply only when a full app-data reset is intended:

```sh
ANDROID_SERIAL=<device-id> npm run storage:cleanup -- --android-app-data --apply --i-understand-this-deletes-kepos-data
```

`smoke:android` assumes the app is already installed on a connected device or emulator and can load
its JS bundle. For the local debug APK, keep Metro running:

```sh
adb reverse tcp:8081 tcp:8081
npm run mobile:start
```

Use `npm run android:assemble` and
`adb install -r android/app/build/outputs/apk/debug/app-debug.apk` when a fresh debug APK is needed.
Use `npm run android:install:release` for the standalone release APK path that does not depend on
Metro.

## Start Desktop

Install desktop runtime dependencies once:

```sh
npm run desktop:install
```

Run the desktop app:

```sh
npm run desktop
```

Expected:

- desktop lobby opens
- profile QR image is visible
- home QR image is visible
- Large Profile QR opens a scan-sized QR dialog
- Large Home QR opens a scan-sized QR dialog
- text URI fields remain available as debug fallback

## Start Android

Run on a connected Android device:

```sh
npm run android
```

Expected:

- Android lobby opens
- profile QR image is visible
- home QR image is visible
- Advanced Scan Home QR and Scan Profile QR open the camera after permission

If testing through ADB, keep the device unlocked. A black screenshot while `dumpsys power` reports
`mWakefulness=Dozing` or while `mCurrentFocus` is `NotificationShade`/`AlternateBouncerView` is
device lock state, not Kepos UI evidence.

Useful checks:

```sh
adb -s <serial> shell dumpsys power | rg 'mWakefulness|mState='
adb -s <serial> shell dumpsys window | rg 'mCurrentFocus|mFocusedApp'
adb -s <serial> shell pidof io.guion.kepos
```

## Two-Device Path

Use one desktop and one Android profile.

1. Desktop: Create Home.
2. Desktop: open Large Profile QR.
3. Android: scan desktop profile QR.
4. Android: trust the desktop profile.
5. Desktop: import or scan Android profile URI.
6. Desktop: trust the Android profile.
7. Desktop: open Large Home QR.
8. Android: scan desktop home QR.
9. Android: join desktop home.
10. Both: verify peer count increases.

Expected:

- raw room keys are not needed for the normal path
- trust is written to ContactBook
- trusted-only home join succeeds only after profile trust exists
- treehole bootstrap and writer capabilities are shared only after the owner sees a signed home hello from a trusted profile

## Room Chat

1. Desktop sends a home chat message.
2. Android receives it.
3. Android sends a home chat message.
4. Desktop receives it.

Expected:

- room chat is ephemeral
- messages appear only in the room chat pane
- Chat panes do not show room chat messages

## Treehole

1. Desktop owner creates a Treehole post.
2. Android sees the post after joining trusted home.
3. Android comments on the post.
4. Android likes the post.
5. Desktop sees the comment and like.

Expected:

- owner can create main posts
- trusted non-owner can comment and like
- trusted non-owner cannot create main posts in the owner's Treehole

## Friend Request And Chat

1. Android opens Chat.
2. Android selects the desktop contact chip.
3. Android sends one friend request.
4. Desktop accepts the request.
5. Both sides show the trusted contact as a Chat recipient option.
6. Android sends a Chat message through the contact chip.
7. Desktop receives it.
8. Desktop replies.
9. Android receives it.
10. Restart both apps and rejoin the home.
11. Send another Chat message.
12. Desktop revokes the Android contact.
13. Android tries to send another Chat message.

Expected:

- friend request and accept travel over profile-level delivery, not Home control
- accepted request creates trust and a durable Chat thread
- signed message bodies use dedicated DM replication, not the home room
- Chat messages persist locally per thread
- Chat messages do not appear in home chat
- revoked contacts are removed from desktop trusted contacts and Chat recipients
- desktop closes the accepted Chat receive path for the revoked contact

## QR Failure Checks

1. Scan a non-Kepos QR.
2. Scan a tampered profile/home URI.
3. Deny camera permission.

Expected:

- invalid QR does not write trust or join home
- tampered signed URI is rejected
- permission denial is visible and does not crash the app

## Known V1 Limits

- each device is its own profile
- revoke blocks future access but does not delete already replicated data
- desktop camera scan is deferred
- manual URI/key entry remains as debug or support fallback
