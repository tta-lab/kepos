# V1 MLP Desktop React Architecture

This document records the V1 MLP direction for the desktop app.

The goal is not to make the current UI look nicer. The goal is to reshape the
desktop app into a product-grade architecture before polishing the interface.

## Decision

Kepos desktop should move to:

```text
Electron renderer React UI
  -> preload/main bridge
  -> Bare worker
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

Mobile keeps the matching shape:

```text
React Native UI
  -> bare-rpc
  -> Bare worklet
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

The shared part is not the visual component tree. The shared part is the
protocol, domain model, backend commands, and session state vocabulary.

## Why Change Desktop

The current desktop app runs, but it is still shaped like a protocol test
client:

- Electron renderer directly owns too much app/backend behavior.
- The UI exposes keys, URIs, profile ids, and status strings as primary product
  objects.
- Desktop and mobile have different runtime boundaries even though both need the
  same P2P backend model.
- V2 and V3 require a stronger local backend boundary for audio streaming, watch
  rooms, local service tunnels, and RetroArch launch/tunnel control.

Running is not the same as being the final architecture.

## Pear/Bare Interpretation

Pear and Bare make the P2P/backend layer portable. They do not make one UI
framework portable across desktop and mobile.

The useful cross-platform idea is:

```text
UI shell -> local bridge/RPC -> Bare backend worker
```

On desktop, the UI shell is Electron. On mobile, the UI shell is React Native.
The backend worker should become the long-lived product core.

This also follows the official Pear desktop pattern more closely: Electron owns
the view layer, and peer-to-peer code lives in a Bare worker behind a bridge.

## Why React On Desktop

Desktop should use React for the MLP UI because the product surface is no longer
a small test page.

The V1 MLP needs:

- a real navigation model for Home, DM, Treehole, and People
- reusable action controls using lucide icons
- stateful empty/loading/error views
- QR dialogs and copy/paste actions
- contact chips, request states, revoke states, and trust flows
- future room surfaces for V2 listening/watch rooms and V3 game sessions

Plain DOM can still do this, but React makes the intended product structure
clearer and easier to maintain.

The reason to use React is not fashion. It is that the UI is becoming a stateful
application, not a static control panel.

## Non-Goals

This decision does not mean:

- sharing one React component tree between desktop and mobile
- using React Native on desktop
- adding a central server
- rewriting the protocol/domain modules
- shipping V2 or V3 features in the V1 MLP pass
- keeping P2P logic in the React renderer

React is the desktop view layer. Bare remains the local backend runtime.

## Target Desktop Boundaries

### Renderer

The renderer should own:

- layout
- components
- local UI state
- form drafts
- dialogs
- route/tab selection
- rendering session snapshots

The renderer should not own:

- Hyperswarm
- Corestore
- Autobase
- treehole replication
- DM replication
- long-running P2P lifecycle
- local service tunnels

### Main / Preload Bridge

The bridge should own:

- starting and stopping the Bare worker
- passing storage paths and launch arguments
- exposing a narrow typed API to the renderer
- forwarding worker events to the renderer
- cleaning up worker lifecycle on quit

The bridge should be small. It is a door, not the app.

### Bare Worker

The worker should own:

- home join/create lifecycle
- P2P room transport
- signed home hello control messages
- treehole open/bootstrap/writer flow
- DM request/invite/thread flow
- persistence adapters that need local backend storage
- future audio/watch/game/tunnel backends

The worker should speak a command/event protocol that mobile can mirror.

## Shared Command Model

Before the React UI gets large, desktop and mobile should converge on a shared
command vocabulary.

Examples:

```text
joinHome
leaveHome
sendHomeMessage
trustProfileUri
joinHomeUri
sendMessageRequest
acceptMessageRequest
sendDmMessage
postTreehole
commentTreehole
likeTreehole
revokeContact
```

Events should also be shared where possible:

```text
statusChanged
peerCountChanged
homeMessageReceived
dmMessageReceived
dmThreadChanged
treeholeStateChanged
contactBookChanged
errorReceived
```

The exact transport can differ between desktop and mobile, but the commands and
payload shapes should not drift without a reason.

- `desktop/app-state.ts` now owns the desktop React state defaults,
  `globalThis.keposDesktopUi` bridge registration, theme persistence, and shell
  busy side effects. `desktop/app.tsx` consumes `useDesktopAppModel()` and stays
  focused on screen composition.
- `desktop/shell-components.jsx` now owns the stable desktop chrome: left rail,

  the state and composition, but no longer carries every shell detail inline.
- `desktop/context-components.jsx` now owns the right context panel's Home,
  Home QR, Profile QR, and trusted-friend form UI. `desktop/app.tsx` still owns
  the context form state and action registration, but no longer embeds the full
  context form markup inline.
- `desktop/people-components.jsx` now owns the People pane, message request
  list, and trusted friend list markup. `desktop/app.tsx` still owns the People
  snapshot state and action callbacks, but no longer embeds the People pane
  surfaces inline.
- `desktop/pane-components.jsx` now owns the Home chat, Direct messages, and
  Treehole pane internals. `desktop/app.tsx` still owns pane state and backend
  action wiring, but no longer embeds composer and message-list surfaces inline.
- `src/desktop-command-vocabulary.ts` records the first V1 MLP command and event
  vocabulary for the desktop bridge.
- `src/desktop-backend-bridge.ts` exposes the renderer-facing backend bridge
  shape for dispatching validated desktop commands and subscribing to validated
  desktop events.
- `src/desktop-command-registry.ts` validates that the desktop controller has a
  handler for every V1 command and exposes one `dispatch(command, payload)` door.
- `src/desktop-dm-runtime.js` moves desktop Direct Message session state, message
  request creation, invite acceptance, thread runtime lifecycle, and DM message
  and thread storage behind a renderer-local runtime boundary.
- `src/desktop-home-runtime.js` moves desktop Home transport, P2P room
  lifecycle, chat session updates, and signed Home hello handling behind a
  renderer-local runtime boundary.
- `src/desktop-treehole-runtime.js` moves desktop Treehole lifecycle,
  replication, state publishing, bootstrap sharing, and writer grants behind a
  renderer-local runtime boundary.
- `src/desktop-backend-runtime.js` composes the Home, Direct Message, and
  Treehole runtimes behind one renderer-local backend facade. It forwards
  runtime updates through the desktop backend event vocabulary and keeps the
  controller from constructing each long-lived runtime directly.
- `src/desktop-backend-subscriptions.ts` owns the renderer-side consumption of
  backend events. It maps Home and Direct Message session snapshots, Treehole
  snapshots, peer counts, and backend errors into controller-owned render hooks
  and state setters.
- `desktop/controller.js` now installs backend subscriptions through that module
  instead of subscribing to each event inline. This keeps renderer session
  rendering on the same event path that preload/main/Bare must use while making
  the controller a thinner coordinator.
- `src/desktop-controller-state.ts` owns the controller's remaining renderer
  snapshot state: desktop view state, Home and Direct Message session snapshots,
  Home join details, current display name, and selected Direct recipient. The
  controller now reads and updates these through one state store instead of
  scattered file-level variables.
- `src/desktop-local-backend-host.ts` composes the desktop command host,
  renderer-local backend bridge, and backend runtime facade. `desktop/controller.js`
  still supplies action implementations and the remaining control-frame
  callbacks, but it no longer wires command dispatch, bridge events, and
  long-lived runtime modules by hand.
- `src/desktop-home-join-service.ts` moves Home join preparation out of
  `desktop/controller.js`: owned homes, manual keys, signed Home QR join
  details, and treehole policy snapshots now come from a DOM-free backend
  service module.
- `src/desktop-qr-service.js` moves desktop Profile QR trust handling, Home QR
  join validation, and signed share QR URI/SVG generation out of
  `desktop/controller.js`. The controller now receives a saved ContactBook
  candidate, treehole policy, joinable Home address, or rendered QR output
  instead of calling signed QR scan primitives or `qrcode` directly.
- `src/desktop-revoke-service.ts` moves desktop contact revoke orchestration out
  of `desktop/controller.js`. It returns updated ContactBook state, DM thread
  changes, revoked runtime thread ids, treehole policy, and recipient-selection

- `src/desktop-message-request-service.ts` moves desktop message request

- `src/desktop-control-service.ts` moves Home control handling for message

## MLP Product Shape

The V1 MLP should make Kepos feel like a private home, not a debugging panel.

Recommended desktop information architecture:

```text
Left rail:
  Home
  DM
  Treehole
  People

Bottom:
  Profile
  Settings / Advanced
  Leave

Main pane:
  Current conversation or room surface

Right pane or modal:
  Home QR
  Profile QR
  trusted people
  session status
```

The main user actions are:

```text
Create My Home
Trust a Friend
Join a Home
Send a Message
Post to Treehole
Revoke Trust
```

Keys and raw ids stay available, but they should move to advanced/debug surfaces.

## Lucide Direction

Use lucide for action language:

- `Home` for home
- `MessageCircle` for chat and DM
- `Sprout` or `Trees` for treehole/private garden
- `Users` for people
- `UserPlus` for trust
- `UserMinus` for revoke
- `QrCode` for share/scan
- `Copy` for copy URI
- `ShieldCheck` for trusted state
- `LogOut` for leave
- `Send` for send
- `Heart` for like

Icons should clarify controls. They should not become decoration.

## Implementation Order

1. Extract desktop backend behavior behind a worker-shaped command/event boundary.
   Current status: in progress. UI actions pass through
   `src/desktop-command-host.ts` and `src/desktop-command-registry.ts`; the
   renderer-local backend assembly lives in `src/desktop-local-backend-host.ts`;
   Home, Direct Message, and Treehole live in renderer-local runtime modules and
   are now composed by `src/desktop-backend-runtime.js`. Home join preparation lives in
   `src/desktop-home-join-service.ts`; QR trust/join validation lives in
   `src/desktop-qr-service.js`; contact revoke orchestration lives in
   `src/desktop-revoke-service.ts`; message request accept/ignore orchestration
   lives in `src/desktop-message-request-service.ts`; Home control handling for
   message requests, DM invites, and Treehole bootstrap/writer grants lives in
   `src/desktop-control-service.ts`. Renderer command/event
   traffic now goes through `src/desktop-renderer-backend-client.ts`, which
   still defaults to the renderer-local backend bridge until the
   preload/main/Bare runtime is wired. Treehole backend storage now receives an
   app-private desktop storage base path from Electron main/preload wiring.
   Local profile and ContactBook access now goes through
   `src/desktop-profile-context.ts`. Signed share QR rendering now lives in
   `src/desktop-qr-service.js`.
2. Move desktop P2P/backend runtime into a Bare worker through `pear-runtime`.
   Current status: app-level desktop smoke proven. Electron main now starts the
   bundled Bare worker through `pear.run()`, connects it through the worker IPC
   client/server bridge, and `npm run smoke:desktop:pear` proves Profile QR,
   Home QR, Home create, and backend state feedback through the real Pear/Bare
   path.
3. Keep the current UI working through the new bridge.
   Current status: done for the basic app path. The React shell receives
   backend snapshots through the preload/main/Bare bridge in Electron, while the
   deterministic in-process stream fallback remains available for fast desktop
   smoke and non-Electron harnesses.
4. Add React build path for the desktop renderer.
   Current status: done for the first shell through `desktop/app.tsx`,
   `react-dom`, `lucide-react`, and the existing `desktop/app.bundle.cjs`
   output.
5. Rebuild the V1 MLP UI in React using the same command/event API.
   Current status: the React shell owns the stable desktop DOM surface and now
   renders the Home chat, Direct message, Direct contact picker, People, and
   Treehole post/comment surfaces, status labels, large QR dialog, and inline
   share QR outputs, plus rail/pane active state and action/composer disabled
   state, shell actions and busy state, plus Home chat, Direct message, and
   Treehole main composer drafts, through a small `globalThis.keposDesktopUi`
   bridge. These content/status surfaces now have snapshot-shaped view-model
   boundaries in `src/desktop-home-chat-view-model.ts`,
   `src/desktop-people-view-model.ts`, `src/desktop-direct-view-model.ts`,
   `src/desktop-direct-contact-picker-view-model.ts`,
   `src/desktop-treehole-view-model.ts`, and `src/desktop-status-view-model.ts`.
6. Align mobile command names and event payloads where they differ.
7. Run desktop smoke, contact smoke, Android bundle checks, and cross-device smoke.

This order avoids mixing architecture migration with visual redesign.

## Risks

### Migration Cost

Moving backend behavior out of the renderer will touch many files.

Mitigation: keep the first worker boundary close to the existing function names
and state snapshots. Do not redesign protocol logic at the same time.

### Duplicate UI Work

Desktop React and React Native will not share components.

Mitigation: share domain state and commands, not components. Copy visual ideas
when useful, but do not force a cross-platform component abstraction.

### Bridge Drift

Desktop and mobile command payloads may diverge.

Mitigation: define shared command/event names in a small module before the React
UI grows.

### Overbuilding MLP

React can tempt the app into adding features while the V1 product still needs
clarity.

Mitigation: V1 MLP changes should only reorganize existing V1 features.

## Recommendation

Use this as the V1 MLP architecture target:

```text
Electron + React + lucide
Bare worker backend via pear-runtime
shared command/event vocabulary with mobile
raw keys and ids hidden behind advanced/debug UI
```

Do the worker split before the full React redesign. The worker split is the
architecture decision. React is the desktop product UI decision.
