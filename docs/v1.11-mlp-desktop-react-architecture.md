# V1 MLP Desktop React Architecture

This document records the V1 MLP direction for the desktop app.

The goal is not to make the current UI look nicer. The goal is to reshape the
desktop app into a product-grade architecture before polishing the interface.

## Decision

Kepos desktop should move to:

```text
Electron renderer React UI
  -> preload/main bridge
  -> Bare worker
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

Mobile keeps the matching shape:

```text
React Native UI
  -> bare-rpc
  -> Bare worklet
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

The shared part is not the visual component tree. The shared part is the
protocol, domain model, backend commands, and session state vocabulary.

## Why Change Desktop

The current desktop app runs, but it is still shaped like a protocol test
client:

- Electron renderer directly owns too much app/backend behavior.
- The UI exposes keys, URIs, profile ids, and status strings as primary product
  objects.
- Desktop and mobile have different runtime boundaries even though both need the
  same P2P backend model.
- V2 and V3 require a stronger local backend boundary for audio streaming, watch
  rooms, local service tunnels, and RetroArch launch/tunnel control.

Running is not the same as being the final architecture.

## Pear/Bare Interpretation

Pear and Bare make the P2P/backend layer portable. They do not make one UI
framework portable across desktop and mobile.

The useful cross-platform idea is:

```text
UI shell -> local bridge/RPC -> Bare backend worker
```

On desktop, the UI shell is Electron. On mobile, the UI shell is React Native.
The backend worker should become the long-lived product core.

This also follows the official Pear desktop pattern more closely: Electron owns
the view layer, and peer-to-peer code lives in a Bare worker behind a bridge.

## Why React On Desktop

Desktop should use React for the MLP UI because the product surface is no longer
a small test page.

The V1 MLP needs:

- a real navigation model for Home, DM, Treehole, and People
- reusable action controls using lucide icons
- stateful empty/loading/error views
- QR dialogs and copy/paste actions
- contact chips, request states, revoke states, and trust flows
- future room surfaces for V2 listening/watch rooms and V3 game sessions

Plain DOM can still do this, but React makes the intended product structure
clearer and easier to maintain.

The reason to use React is not fashion. It is that the UI is becoming a stateful
application, not a static control panel.

## Non-Goals

This decision does not mean:

- sharing one React component tree between desktop and mobile
- using React Native on desktop
- adding a central server
- rewriting the protocol/domain modules
- shipping V2 or V3 features in the V1 MLP pass
- keeping P2P logic in the React renderer

React is the desktop view layer. Bare remains the local backend runtime.

## Target Desktop Boundaries

### Renderer

The renderer should own:

- layout
- components
- local UI state
- form drafts
- dialogs
- route/tab selection
- rendering session snapshots

The renderer should not own:

- Hyperswarm
- Corestore
- Autobase
- treehole replication
- DM replication
- long-running P2P lifecycle
- local service tunnels

### Main / Preload Bridge

The bridge should own:

- starting and stopping the Bare worker
- passing storage paths and launch arguments
- exposing a narrow typed API to the renderer
- forwarding worker events to the renderer
- cleaning up worker lifecycle on quit

The bridge should be small. It is a door, not the app.

### Bare Worker

The worker should own:

- home join/create lifecycle
- P2P room transport
- signed home hello control messages
- treehole open/bootstrap/writer flow
- DM request/invite/thread flow
- persistence adapters that need local backend storage
- future audio/watch/game/tunnel backends

The worker should speak a command/event protocol that mobile can mirror.

## Shared Command Model

Before the React UI gets large, desktop and mobile should converge on a shared
command vocabulary.

Examples:

```text
joinHome
leaveHome
sendHomeMessage
trustProfileUri
joinHomeUri
sendMessageRequest
acceptMessageRequest
sendDmMessage
postTreehole
commentTreehole
likeTreehole
revokeContact
```

Events should also be shared where possible:

```text
statusChanged
peerCountChanged
homeMessageReceived
dmMessageReceived
dmThreadChanged
treeholeStateChanged
contactBookChanged
errorReceived
```

The exact transport can differ between desktop and mobile, but the commands and
payload shapes should not drift without a reason.

Current implementation status:

- `src/desktop-command-vocabulary.ts` records the first V1 MLP command and event
  vocabulary for the desktop bridge.
- `src/desktop-backend-bridge.ts` exposes the renderer-facing backend bridge
  shape for dispatching validated desktop commands and subscribing to validated
  desktop events.
- `src/desktop-command-registry.ts` validates that the desktop controller has a
  handler for every V1 command and exposes one `dispatch(command, payload)` door.
- `src/desktop-dm-runtime.js` moves desktop Direct Message session state, message
  request creation, invite acceptance, thread runtime lifecycle, and DM message
  and thread storage behind a renderer-local runtime boundary.
- `src/desktop-home-runtime.js` moves desktop Home transport, P2P room
  lifecycle, chat session updates, and signed Home hello handling behind a
  renderer-local runtime boundary.
- `src/desktop-treehole-runtime.js` moves desktop Treehole lifecycle,
  replication, state publishing, bootstrap sharing, and writer grants behind a
  renderer-local runtime boundary.
- `src/desktop-backend-runtime.js` composes the Home, Direct Message, and
  Treehole runtimes behind one renderer-local backend facade. It forwards
  runtime updates through the desktop backend event vocabulary and keeps the
  controller from constructing each long-lived runtime directly.
- `src/desktop-home-join-service.js` moves Home join preparation out of
  `desktop/controller.js`: owned homes, manual keys, signed Home QR join
  details, and treehole policy snapshots now come from a DOM-free backend
  service module.
- `src/desktop-qr-service.js` moves desktop Profile QR trust handling, Home QR
  join validation, and signed share QR URI/SVG generation out of
  `desktop/controller.js`. The controller now receives a saved ContactBook
  candidate, treehole policy, joinable Home address, or rendered QR output
  instead of calling signed QR scan primitives or `qrcode` directly.
- `src/desktop-revoke-service.js` moves desktop contact revoke orchestration out
  of `desktop/controller.js`. It returns updated ContactBook state, DM thread
  changes, revoked runtime thread ids, treehole policy, and recipient-selection
  cleanup intent as one backend result.
- `src/desktop-message-request-service.js` moves desktop message request
  accept/ignore orchestration out of `desktop/controller.js`. The controller now
  asks the service for ContactBook changes, DM invite broadcasts, and optional
  local DM message dismissal instead of mutating ContactBook request state
  directly.
- `src/desktop-control-service.js` moves Home control handling for message
  requests, DM invites, and Treehole bootstrap/writer grants out of
  `desktop/controller.js`. The controller now receives a ContactBook update,
  incoming request append intent, accepted invite result, Treehole open intent,
  writer grant intent, or outbound Treehole send intent instead of deciding
  those protocol transitions inline.
- `src/desktop-home-chat-view-model.js` moves Home chat list display data out of
  `desktop/controller.js`. `desktop/app.jsx` now owns the React-rendered Home
  chat list, while the controller pushes snapshot-shaped row data through the
  renderer UI bridge.
- `src/desktop-people-view-model.js` moves People panel display data for trusted
  contacts and message requests out of `desktop/controller.js`. `desktop/app.jsx`
  now owns the React-rendered People lists, while the controller pushes
  snapshot-shaped contact/request data and accept/ignore/revoke callbacks through
  the renderer UI bridge.
- `src/desktop-direct-view-model.js` moves Direct message list display data out
  of `desktop/controller.js`. `desktop/app.jsx` now owns the React-rendered
  Direct message list, while the controller pushes snapshot-shaped row data and
  accept/ignore callbacks through the renderer UI bridge.
- `src/desktop-direct-contact-picker-view-model.js` moves Direct message
  contact picker display data out of `desktop/controller.js`. `desktop/app.jsx`
  now owns the trusted-contact picker and zero-contact empty state, while the
  controller pushes contact snapshots and selection/open-People callbacks
  through the renderer UI bridge.
- `src/desktop-treehole-view-model.js` moves Treehole post/comment display data
  out of `desktop/controller.js`. `desktop/app.jsx` now owns the React-rendered
  Treehole post/comment list, inline comment draft state, and main post composer
  draft state, while the controller pushes snapshot-shaped rows and
  like/comment callbacks through the renderer UI bridge.
- `src/desktop-status-view-model.js` moves desktop status, notice, advanced
  profile/home ids, peer count, and error-detail display data out of
  `desktop/controller.js`. `desktop/app.jsx` now owns these labels, while the
  controller pushes one status snapshot through the renderer UI bridge.
- `desktop/app.jsx` now owns the large QR dialog state through
  `globalThis.keposDesktopUi.setLargeQr()`. The controller still decides when to
  open, close, and restore focus, but it no longer mutates the dialog title or
  QR SVG DOM.
- `desktop/app.jsx` now owns the inline profile/home share QR outputs through
  `globalThis.keposDesktopUi.setShareQrOutputs()`. The controller creates the
  signed QR payloads, but React renders the SVG and read-only URI details.
- `desktop/app.jsx` now owns context-panel form drafts and actions through
  `globalThis.keposDesktopUi.setContextFormActions()` and
  `setContextFormDraft()`: display name, manual home key, Home QR paste, Profile
  QR paste, and trust alias are React-controlled. The controller still executes
  Home join, QR trust, QR copy, and large-QR commands, but it no longer reads,
  listens to, or clears those form DOM nodes.
- `desktop/app.jsx` now owns desktop rail active state and pane visibility
  through `globalThis.keposDesktopUi.setActiveTab()`. The controller still
  updates desktop state, but React handles tab clicks and renders active
  classes, hidden panes, and `aria-current`.
- `desktop/app.jsx` now owns shell action glue and busy state through
  `globalThis.keposDesktopUi.setShellActions()` and `setShellBusy()`. React
  handles rail tab clicks, the leave-home button, large QR close button,
  overlay/Escape close behavior, and `body[aria-busy]`. The controller still
  owns command dispatch and large QR focus restoration, but it no longer queries
  or listens to shell buttons and dialog DOM nodes directly.
- `desktop/app.jsx` now owns action and composer disabled state through
  `globalThis.keposDesktopUi.setControls()`. The controller still calculates
  runtime availability, but React renders button disabled states and composer
  draft-dependent disabled states.
- `desktop/app.jsx` now owns the Home chat composer draft and submit flow through
  `globalThis.keposDesktopUi.setHomeComposerActions()`. The controller still
  owns Home message production, but it no longer reads or clears the Home chat
  input DOM.
- `desktop/app.jsx` now owns the Direct message composer draft, selected
  recipient, advanced manual recipient input, and submit flow through
  `globalThis.keposDesktopUi.setDirectComposerActions()`. The controller keeps a
  plain selected-recipient id for contact selection and revoke cleanup, but it no
  longer reads, listens to, or clears the Direct message input DOM.
- `desktop/app.jsx` now owns the Treehole main post composer draft and submit
  flow through `globalThis.keposDesktopUi.setTreeholeComposerActions()`. The
  controller still owns Treehole runtime post calls, but it no longer reads or
  clears the Treehole input DOM.
- `src/desktop-renderer-backend-client.js` gives the renderer one command/event
  client. It uses the renderer-local bridge by default and can explicitly switch
  to the preload bridge once the main/Bare runtime is connected.
- `src/desktop-command-host.js` owns V1 desktop command-to-action mapping and
  payload normalization. `desktop/controller.js` still supplies the action
  implementations for now, but it no longer constructs the command registry or
  normalizes command payloads inline.
- Home chat, Direct message, and Treehole composer submits now dispatch explicit
  command payloads instead of having those command handlers read composer text
  directly from DOM elements. This starts moving renderer-owned form drafts out
  of backend command execution.
- Home QR join, manual Home join, Profile QR trust, QR copy, and large-QR actions
  now dispatch explicit renderer payloads or callbacks from React instead of
  having command handlers read context-panel form text directly from DOM nodes.
- `src/desktop-profile-context.js` centralizes desktop local profile,
  ContactBook load, and ContactBook save access. `desktop/controller.js` now
  depends on that profile context instead of importing low-level local adapters
  directly.
- `src/desktop-storage-base.js` and the Electron main/preload wiring expose an
  app-private desktop storage base path. `src/desktop-backend-runtime.js` passes
  that base path into the Treehole runtime, which now uses the shared
  `createTreeholeStoragePath()` helper instead of hard-coding treehole storage
  under the user home directory.
- `desktop/electron/preload.cjs` and `desktop/electron/backend-ipc.cjs` add the
  first Electron preload/main IPC bridge skeleton. It exposes a narrow
  `window.keposBackend` dispatch/subscribe API, validates command/event names in
  main, can retarget events to a recreated window, and can connect a real
  backend dispatch after registration. The V1 business runtime still runs in the
  renderer for now.
- `test/desktop-command-vocabulary.test.js` keeps the vocabulary explicit and
  rejects unknown command/event names.
- `test/desktop-backend-bridge.test.js` keeps the bridge aligned with the shared
  command/event vocabulary.
- `test/desktop-command-host.test.js` keeps V1 desktop command mapping and
  payload normalization outside `desktop/controller.js`.
- `test/desktop-command-registry.test.js` keeps the registry complete and checks
  that desktop UI actions route through the command host.
- This is not the Bare worker bridge yet. It is the renderer-facing bridge API,
  naming SSOT, and first runtime seams that the worker migration should
  preserve.

## MLP Product Shape

The V1 MLP should make Kepos feel like a private home, not a debugging panel.

Recommended desktop information architecture:

```text
Left rail:
  Home
  DM
  Treehole
  People

Bottom:
  Profile
  Settings / Advanced
  Leave

Main pane:
  Current conversation or room surface

Right pane or modal:
  Home QR
  Profile QR
  trusted people
  session status
```

The main user actions are:

```text
Create My Home
Trust a Friend
Join a Home
Send a Message
Post to Treehole
Revoke Trust
```

Keys and raw ids stay available, but they should move to advanced/debug surfaces.

## Lucide Direction

Use lucide for action language:

- `Home` for home
- `MessageCircle` for chat and DM
- `Sprout` or `Trees` for treehole/private garden
- `Users` for people
- `UserPlus` for trust
- `UserMinus` for revoke
- `QrCode` for share/scan
- `Copy` for copy URI
- `ShieldCheck` for trusted state
- `LogOut` for leave
- `Send` for send
- `Heart` for like

Icons should clarify controls. They should not become decoration.

## Implementation Order

1. Extract desktop backend behavior behind a worker-shaped command/event boundary.
   Current status: in progress. UI actions pass through
   `src/desktop-command-host.js` and `src/desktop-command-registry.ts`; Home,
   Direct Message, and Treehole live in renderer-local runtime modules and are
   now composed by `src/desktop-backend-runtime.js`. Home join preparation lives in
   `src/desktop-home-join-service.js`; QR trust/join validation lives in
   `src/desktop-qr-service.js`; contact revoke orchestration lives in
   `src/desktop-revoke-service.js`; message request accept/ignore orchestration
   lives in `src/desktop-message-request-service.js`; Home control handling for
   message requests, DM invites, and Treehole bootstrap/writer grants lives in
   `src/desktop-control-service.js`. Renderer command/event
   traffic now goes through `src/desktop-renderer-backend-client.js`, which
   still defaults to the renderer-local backend bridge until the
   preload/main/Bare runtime is wired. Treehole backend storage now receives an
   app-private desktop storage base path from Electron main/preload wiring.
   Local profile and ContactBook access now goes through
   `src/desktop-profile-context.js`. Signed share QR rendering now lives in
   `src/desktop-qr-service.js`.
2. Move desktop P2P/backend runtime into a Bare worker through `pear-runtime`.
   Current status: pending. The Electron preload/main IPC bridge skeleton now
   exists, but it is not yet connected to the backend runtime or Bare worker.
3. Keep the current UI working through the new bridge.
   Current status: pending Bare bridge, but `desktop/controller.js` preserves
   current behavior behind the React shell and delegates Home, Direct Message,
   and Treehole runtime work through the backend runtime facade.
4. Add React build path for the desktop renderer.
   Current status: done for the first shell through `desktop/app.jsx`,
   `react-dom`, `lucide-react`, and the existing `desktop/app.bundle.cjs`
   output.
5. Rebuild the V1 MLP UI in React using the same command/event API.
   Current status: the React shell owns the stable desktop DOM surface and now
   renders the Home chat, Direct message, Direct contact picker, People, and
   Treehole post/comment surfaces, status labels, large QR dialog, and inline
   share QR outputs, plus rail/pane active state and action/composer disabled
   state, shell actions and busy state, plus Home chat, Direct message, and
   Treehole main composer drafts, through a small `globalThis.keposDesktopUi`
   bridge. These content/status surfaces now have snapshot-shaped view-model
   boundaries in `src/desktop-home-chat-view-model.js`,
   `src/desktop-people-view-model.js`, `src/desktop-direct-view-model.js`,
   `src/desktop-direct-contact-picker-view-model.js`,
   `src/desktop-treehole-view-model.js`, and `src/desktop-status-view-model.js`.
6. Align mobile command names and event payloads where they differ.
7. Run desktop smoke, contact smoke, Android bundle checks, and cross-device smoke.

This order avoids mixing architecture migration with visual redesign.

## Risks

### Migration Cost

Moving backend behavior out of the renderer will touch many files.

Mitigation: keep the first worker boundary close to the existing function names
and state snapshots. Do not redesign protocol logic at the same time.

### Duplicate UI Work

Desktop React and React Native will not share components.

Mitigation: share domain state and commands, not components. Copy visual ideas
when useful, but do not force a cross-platform component abstraction.

### Bridge Drift

Desktop and mobile command payloads may diverge.

Mitigation: define shared command/event names in a small module before the React
UI grows.

### Overbuilding MLP

React can tempt the app into adding features while the V1 product still needs
clarity.

Mitigation: V1 MLP changes should only reorganize existing V1 features.

## Recommendation

Use this as the V1 MLP architecture target:

```text
Electron + React + lucide
Bare worker backend via pear-runtime
shared command/event vocabulary with mobile
raw keys and ids hidden behind advanced/debug UI
```

Do the worker split before the full React redesign. The worker split is the
architecture decision. React is the desktop product UI decision.
