# V2 Shared Music Room

This document records the V2B direction for Kepos listening rooms.

The decision is deliberately narrow: the first listening room is a shared music
room over a NAS-backed or self-hosted music service. It is not a live singing
room, karaoke room, recording workflow, or Kepos-owned music server.

## Decision

Kepos V2B should model a listening room as:

```text
self-hosted music service
  -> Kepos local P2P proxy
  -> shared room playback
```

The preferred first adapter is a Subsonic-compatible service such as Navidrome.
A generic HTTP music directory can be a later or lower-level fallback, but the
main product should be adapter-led rather than raw port sharing.

The room has one shared queue, one current track, and one shared playback state.
Authorized room members can add songs and control playback by default. Every
listener should hear the same track at roughly the same position.

## Why

The product sentence should stay simple:

```text
Friends listen together from a self-hosted music library.
```

This fits the broader V2 direction: mature self-hosted products own media
complexity, while Kepos owns the trusted shared-space layer.

Kepos should not rebuild:

- library scanning
- metadata
- artwork
- playlist storage
- transcoding
- music server auth
- long-term playback history

Kepos should add:

- trusted room membership
- signed room controls
- shared queue state
- shared playback clock
- local P2P access to the owner's music service
- revoke, expiry, and clear stop controls

## Scope

In scope:

- desktop first
- owner-configured self-hosted music service
- trusted room participants
- shared queue
- play, pause, seek, skip, add, remove, and reorder controls
- new listeners joining at the current track position
- room chat alongside music
- rough sync, usually within about 500 ms under normal conditions

Out of scope:

- live singing
- karaoke
- microphone capture
- recording requests
- Kepos-owned music upload
- public music catalogs
- public rooms
- generic NAS browsing
- arbitrary LAN routing
- Kepos-owned transcoding
- sample-accurate sync

Recording requests can live in an external table until the music room itself is
proven.

## Session Shape

```ts
type MusicRoomSession = {
  type: 'kepos.music-room.session.v1'
  version: 1
  sessionId: string
  homeOwnerProfileId: string
  hostProfileId: string
  source: {
    service: 'subsonic' | 'navidrome' | 'generic_http'
    baseUrlLabel: string
  }
  state: 'idle' | 'playing' | 'paused' | 'stopped' | 'failed'
  createdAt: number
  startedAt?: number
  stoppedAt?: number
}

type MusicRoomState = {
  sessionId: string
  queue: MusicTrack[]
  currentTrackId: string | null
  playback: {
    status: 'playing' | 'paused'
    trackStartedAtRoomTime: number
    positionMsAtStartedAt: number
    version: number
  }
  controllerProfileIds: string[]
}
```

Session and playback records that affect shared state should be signed by the
profile that sends them.

## Playback Sync

Each client computes the expected local playback position from the room clock:

```text
targetPosition =
  positionMsAtStartedAt + (nowRoomTime - trackStartedAtRoomTime)
```

Suggested correction policy:

- ignore drift below 150 ms
- use slight playback-rate correction for medium drift
- seek for large drift, such as more than 800 ms
- discard stale playback events by `version`

This is not a hard real-time audio system. The goal is that people in the room
hear the same song and stay close enough for normal shared listening.

## Media Path

Target path:

```text
Navidrome or Subsonic-compatible service
  -> owner Kepos local P2P proxy
  -> listener Kepos local proxy
  -> listener audio player
```

Room state remains separate:

```text
room chat frames != music control frames != media bytes
```

The proxy moves media bytes and media assets. Kepos control messages move queue
and playback state.

## Product Rules

- only trusted room members can join
- authorized room members can control playback by default
- owner can close the room
- owner can remove controller permission if needed later
- revoke closes relevant access
- the music service share is explicit and room-scoped
- stopping the room closes the local service share

## Technical Questions

Before implementation, investigate:

- first Subsonic API surface needed for browse, search, stream URL, artwork, and
  track metadata
- whether the player should stream through the local proxy as a normal URL or
  through a Kepos-owned fetch layer
- how to estimate room clock drift between peers
- how browser or Electron audio playback rate correction behaves across
  platforms
- how to avoid exposing broad music server admin access through the proxy
- whether guest-side requests should be signed or bound to one room capability

## Implementation Order

1. Music room domain model

   Add session shape, queue state, playback state, and signed control records.

2. Local self-hosted service probe

   Connect to one local Navidrome or Subsonic-compatible service and list/search
   tracks.

3. Local P2P proxy probe

   Stream one track through the room-scoped local proxy.

4. Shared playback

   Add play, pause, seek, skip, and join-at-current-position behavior.

5. Home UI

   Show the music room state, current track, queue, listeners, and controls.

6. Hardening

   Handle missing service, expired share, revoke, playback drift, stream
   failure, and closed room.

## Success Bar

V2B is useful when:

- Neil's music lives in a NAS-backed Navidrome or Subsonic-compatible service.
- Neil opens a music room in his home.
- Ada joins as a trusted listener.
- Ada adds a song to the queue.
- Neil and Ada hear the same track.
- Ada pauses and both clients pause.
- Neil skips and both clients move to the next track.
- a new listener joins and seeks to the current track position.
- stopping the room closes playback and the service share cleanly.

The first version does not need recording requests, karaoke, music upload, or
Kepos-owned transcoding.
