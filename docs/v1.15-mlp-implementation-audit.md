# V1 MLP Implementation Audit

This audit records the current V1 MLP state after the React desktop shell and
mobile UX polish passes.

## Verdict

V1 is close on product UX, shared domain behavior, and the desktop runtime
shape. The desktop Electron path now has app-level proof that it can run the
backend through `pear-runtime` and a bundled Bare worker. The remaining V1 risk
is no longer the basic desktop worker bridge; it is broader cross-device,
restart, and long-running product proof.

## Shared Model Status

The shared V1 model is substantially complete:

- one device is one profile
- profile id is the identity public key
- one profile owns one home
- ContactBook is the local trust state
- signed Profile QR can be read as a friend-request target without creating trust
- signed Profile QR can refresh a profile-owned Home descriptor without changing
  the authorization model
- friend request acceptance creates the mutual trust relationship
- signed Home QR checks trusted-only access
- treehole signed mode enforces owner main posts and trusted interactions
- message requests are bounded and do not grant home access
- accepted requests create durable pairwise DM threads
- signed DM bodies use dedicated pairwise replication channels
- DM invite acceptance rejects revoked senders before honoring request-bound
  platform exceptions
- DM runtime verifies channel-delivered messages before persistence or UI
  display, so it does not rely only on the lower replication adapter to filter
  invalid signed messages
- revoke updates trust, clears pending requests from the revoked profile,
  updates treehole policy, DM thread state, and active DM runtime

## Completion Evidence And Release Proof

### 1. Desktop Bare Worker Bridge

Status: done for V1 architecture proof; broader cross-device proof remains.

`docs/v1.11-mlp-desktop-react-architecture.md` says desktop should become:

```text
Electron renderer React UI
  -> preload/main bridge
  -> Bare worker
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

Current implementation has split the renderer controller into worker-shaped
runtime boundaries:

- `src/desktop-dm-runtime.ts` owns desktop Chat session state, message
  request creation, invite acceptance, thread runtime lifecycle, and DM message

- `src/desktop-home-runtime.ts` owns desktop Home transport, P2P room lifecycle,

  instead of wiring every backend event inline.
- `src/desktop-controller-state.ts` owns the controller's remaining renderer

  Home join details, current display name, and selected message recipient. This

### 2. Desktop Dynamic Lists Are React-Owned

Status: done for the main dynamic list surfaces.

React owns the stable desktop shell, Home chat list, Chat list, Chat
trusted-contact picker, Contacts lists, Treehole post/comment rows, and
desktop status labels, plus the large QR dialog, inline share QR outputs, and
rail/pane active state, action/composer disabled state, and the Home chat,
Chat, Treehole main post, and context-panel form drafts.

Home chat rows, Contacts contacts/message requests, Chat rows, Chat
trusted-contact picker rows, Treehole post/comment rows, and status
labels now have separate view-model boundaries in
`src/desktop-home-chat-view-model.ts`, `src/desktop-people-view-model.ts`,
`src/desktop-direct-view-model.ts`,
`src/desktop-direct-contact-picker-view-model.ts`, and
`src/desktop-treehole-view-model.ts`, and `src/desktop-status-view-model.ts`.
These surfaces feed React components through the renderer UI bridge.

Repeated content, status, navigation, QR display, shell actions, busy state,
disabled-state, Home chat draft, Chat draft/recipient, Treehole main
post draft, and context-panel form draft surfaces no longer require imperative
DOM construction.

The current React shell has first-pass MLP polish for theme, focus, hover,
navigation, and narrow-screen layout. Future desktop UI work should keep React
fed by snapshots, drafts, and explicit command payloads instead of adding
controller DOM listeners back.

### 3. Live Cross-Device Proof Remains Debug-Heavy

Status: acceptable for iteration, not final proof.

The debug two-device script targets live transport behavior, but part of the path
uses debug setup rather than the fully normal physical QR flow. `smoke:two-device:debug` now passes
on a connected Pixel 7a dev-client setup, and `smoke:two-device:debug:pear` proves the same
cross-device path with the desktop side on the bundled worker bridge. The screen-to-camera QR proof
also passed for the Profile QR trust path and the Advanced Debug Home QR scan path after trust already
exists on the connected Pixel 7a. These are strong
sub-proofs, but final release proof still needs the normal product path in one run: Profile QR
scan, friend request, ignored request recovery, second request acceptance, Chat, trusted
profile, explicit Home entry, Treehole, restart, and revoke.

Release-readiness evidence should include manual smoke for final V1 confidence,
plus `smoke:two-device:debug:pear` when desktop bridge changes need
cross-device evidence. Avoid making fragile smoke work the main implementation
thread unless the work is specifically release proof.

## Non-Blocking For V1

These are not V1 blockers:

- desktop camera scan
- key rotation after revoke
- compact binary QR payloads
- multi-device identity
- safety-number compare UX
- V2 listening/watch room features
- V3 RetroArch or local service tunnels

## Next Best Work After MLP

The next implementation phase should close concrete gaps found by gates,
manual smoke, debug cross-device smoke, or PR review. The broad architecture
shape is in place: React-owned product surfaces, backend bridge snapshots,
signed trust and treehole rules, durable message threads, request restart
display on desktop and Android, and Pear/Bare desktop worker proof. The
highest-value remaining V1 work is evidence-driven hardening: cross-device
repetition, restart behavior, failure handling, and any product-path defects
those runs expose.
