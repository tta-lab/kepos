# V1 MLP Implementation Audit

This audit records the current V1 MLP state after the React desktop shell and
mobile UX polish passes.

## Verdict

V1 is close on product UX, shared domain behavior, and the desktop runtime
shape. The desktop Electron path now has app-level proof that it can run the
backend through `pear-runtime` and a bundled Bare worker. The remaining V1 risk
is no longer the basic desktop worker bridge; it is broader cross-device,
restart, and long-running product proof.

## Product UX Status

Current evidence says the normal V1 loop no longer depends on raw keys as the
primary user path:

- desktop has Home, Direct, Treehole, and People navigation
- mobile has Home, Direct, Treehole, and People tabs
- Profile QR and Home QR are the normal trust and join surfaces
- manual home keys and manual DM recipient ids stay in Advanced
- desktop and mobile use product words for Home, People, Direct messages, and
  Treehole
- desktop and mobile expose empty, disabled, and short error states for the main
  V1 surfaces
- desktop primary panes now use shared product headers with short guidance copy,
  reducing duplicated React chrome while making live, durable, and trust surfaces
  easier to understand
- desktop right context forms now use shared task panel headers for setup,
  sharing/joining, and trusted-friend entry actions, making the first-run path
  easier to scan without changing command wiring
- mobile QuickStart and People setup panels now use a shared task header for
  start, invite, and trust actions, keeping first-run mobile hierarchy aligned
  with the desktop MLP shell without changing QR or trust command wiring
- mobile People management panels now reuse that same task header for message
  requests and trusted friends, so trust-management UI is consistent across
  request, invite, and contact surfaces
- mobile Advanced panels for manual Home keys and raw QR details now reuse the
  same task header shape, keeping debug-only paths aligned without promoting
  raw keys or payloads into the normal flow
- mobile setup buttons now use icons consistently for scan, trust, and Advanced
  actions, improving first-run scannability without changing command wiring
- mobile room tabs now use icon-plus-label navigation for Home, Direct,
  Treehole, and People while preserving selected accessibility state
- desktop and mobile navigation surfaces pending Direct and People work through
  badges, with pending counts included in navigation accessibility labels
- desktop People empty panels now use icon-led product empty states for message
  requests and trusted friends, keeping trust management readable before any
  requests or contacts exist
- desktop Home, Direct, and Treehole empty states now render as real icon-led
  list items rather than CSS-generated text, keeping blank panes accessible and
  visually aligned with the People empty panels
- mobile Home, Direct, and Treehole empty states now share one layout component
  with contextual icons, keeping first-run quiet states consistent
- mobile Direct's zero-contact state now reuses that same icon-led empty
  treatment before linking users to People for trust setup
- desktop Direct's zero-contact contact picker now uses an icon-led empty state
  and an explicit People action, keeping the first Direct message path aligned
  with the rest of the MLP empty-state system
- desktop and mobile trusted-friend metadata now use Home instead of Home room,
  keeping internal room terminology out of normal trust surfaces
- mobile room Advanced controls now use the same icon treatment as setup and
  Direct advanced controls while keeping raw details hidden by default
- mobile People empty management panels now share one icon-led layout for
  message requests and trusted friends
- desktop and mobile Direct guide zero-contact users toward People/trust instead
  of the manual recipient debug path
- mobile QR scanner has cancel and permission-denied states
- desktop large QR dialogs are keyboard reachable

## Shared Model Status

The shared V1 model is substantially complete:

- one device is one profile
- profile id is the identity public key
- one profile owns one home
- ContactBook is the local trust state
- signed Profile QR creates trust
- signed Home QR checks trusted-only access
- treehole signed mode enforces owner main posts and trusted interactions
- message requests are bounded and do not grant home access
- accepted requests create durable pairwise DM threads
- signed DM bodies use dedicated pairwise replication channels
- revoke updates trust, treehole policy, DM thread state, and active DM runtime

## Remaining Required Work

### 1. Desktop Bare Worker Bridge

Status: done for V1 architecture proof; broader cross-device proof remains.

`docs/v1.11-mlp-desktop-react-architecture.md` says desktop should become:

```text
Electron renderer React UI
  -> preload/main bridge
  -> Bare worker
  -> Hyperswarm / Corestore / Autobase / DM / Treehole
```

Current implementation has split the renderer controller into worker-shaped
runtime boundaries:

- `src/desktop-dm-runtime.js` owns desktop Direct Message session state, message
  request creation, invite acceptance, thread runtime lifecycle, and DM message
  and thread storage
- `src/desktop-home-runtime.js` owns desktop Home transport, P2P room lifecycle,
  chat session updates, and signed Home hello handling
- `src/desktop-treehole-runtime.js` owns desktop Treehole lifecycle,
  replication, state publishing, bootstrap sharing, and writer grants
- `src/desktop-backend-runtime.js` composes those three runtime modules behind
  one renderer-local backend facade and forwards runtime updates through the
  desktop backend event vocabulary
- `src/desktop-backend-subscriptions.js` owns renderer-side backend event
  subscriptions for Home and Direct Message sessions, Treehole snapshots, peer
  counts, backend errors, ContactBook snapshots, desktop state snapshots,
  context-form drafts, Direct recipient drafts, and share QR outputs
- `desktop/controller.js` now installs those subscriptions through one module
  instead of wiring every backend event inline.
- `src/desktop-controller-state.js` owns the controller's remaining renderer
  snapshot state: desktop view state, Home and Direct Message session snapshots,
  Home join details, current display name, and selected Direct recipient. This
  removes the remaining file-level mutable state variables from
  `desktop/controller.js`.
- `src/desktop-home-join-service.js` owns DOM-free Home join preparation for
  owned homes, manual keys, signed Home QR join details, and treehole policy
  snapshots
- `src/desktop-qr-service.js` owns DOM-free desktop Profile QR trust handling,
  Home QR join validation, and signed share QR URI/SVG generation
- `src/desktop-revoke-service.js` owns DOM-free desktop contact revoke
  orchestration across ContactBook, DM thread state, treehole policy, and
  recipient-selection cleanup intent
- `src/desktop-message-request-service.js` owns DOM-free desktop message request
  accept/ignore orchestration across ContactBook updates, DM invite broadcasts,
  and local DM request dismissal intent
- `src/desktop-control-service.js` owns DOM-free Home control handling for
  message requests, DM invites, and Treehole bootstrap/writer grants, including
  ContactBook updates, incoming request append intent, accepted invite
  transitions, Treehole open intent, writer grant intent, and outbound Treehole
  send intent
- `desktop/app-state.jsx` now owns the desktop React state defaults, renderer
  bridge registration, theme persistence, and shell busy side effects.
  `desktop/app.jsx` consumes `useDesktopAppModel()` so the entry component is
  mostly screen composition instead of bridge wiring.
- `desktop/shell-components.jsx` now owns the stable desktop shell chrome: left

- `desktop/context-components.jsx` now owns the desktop context panel markup for

  callbacks, but the main app component no longer embeds all context controls.
- `desktop/people-components.jsx` now owns the desktop People pane and list

- `desktop/pane-components.jsx` now owns the desktop Home chat, Direct messages,
  and Treehole pane internals. `desktop/app.jsx` still owns the state and action
  wiring, but the main app component no longer embeds the primary composer and

- `src/desktop-home-chat-view-model.js` owns snapshot-shaped display data for
  desktop Home chat rows, including incoming/outgoing classes, sender labels,

- `desktop/app.jsx` now renders Home chat rows in React through
  `globalThis.keposDesktopUi.setHomeMessages()`. `src/desktop-render-presenter.js`

- `src/desktop-people-view-model.js` owns snapshot-shaped display data for

- `src/desktop-direct-view-model.js` owns snapshot-shaped display data for
  desktop Direct message rows, including incoming/outgoing classes, meta labels,

- `desktop/app.jsx` now renders Direct message rows in React through

- `src/desktop-direct-contact-picker-view-model.js` owns snapshot-shaped display

- `desktop/app.jsx` now renders the Direct message trusted-contact picker in

  starts the worker entry, and exposes the IPC client bridge to Electron main.

  forwards connected backend events through the Electron bridge. The renderer

- `src/desktop-backend-worker-ipc.js` now defines the stream protocol needed for

  replays latest snapshot events to late subscribers and preserves `Map`, `Set`,

- `src/desktop-backend-worker-bare-entry.js` is now the Bare-side entrypoint for

  reads the desktop storage base path from the worker argv passed by Electron
  main. It installs `bare-encoding` TextEncoder/TextDecoder globals for shared
  WebCrypto-style helpers used inside the Bare worker.
- Electron main now passes `pear.run(workerEntryPath, [storageBasePath])` into

  deterministic path remains available, and `smoke:desktop:pear` exercises the

- `desktop/backend-worker.bundle.cjs` is now built from the Bare worker entry so
  the worker does not ask Bare to load raw TypeScript or Node-only source

  `desktop/backend-worker.bundle.cjs` and dispatched `updateDisplayName` through
  `src/desktop-backend-worker-ipc.js` successfully. That proves the current

- `npm run smoke:desktop:pear` now launches the Electron app without

- `npm run smoke:desktop:contacts:pear` now runs Profile QR trust and ContactBook

  This extends desktop worker proof beyond basic Home creation into trusted

  revoke persistence.
- `desktopStateChanged` is now part of the desktop backend event vocabulary.
  Main-side backend session changes publish desktop state snapshots through the
  bridge, and renderer subscriptions can replace their local state from that

  renderer-local backend fallback.
- `contactBookChanged` is now used as a backend snapshot event. Main-side

  renderer keeps a backend ContactBook snapshot for People and Direct contact

  P2P backend.
- The renderer controller and renderer-local fallback backend now build as
  separate bundles: `controller.browser.bundle.js`, `controller.bundle.cjs`, and
  `local-backend.bundle.cjs`. `desktop/controller.js` loads the local backend
  bundle only when the fallback path is needed, so the Electron browser
  controller bundle no longer statically contains Hyperswarm/Corestore/Autobase
  runtime code.
- The renderer-local profile and QR fallback now builds as
  `local-profile.bundle.cjs`. `desktop/controller.js` loads it lazily only for
  local profile context, file storage base lookup, and QR SVG/payload creation,
  so `controller.bundle.cjs` no longer statically contains QR, sodium,
  hypercore-crypto, compact-encoding, b4a, or node `fs`/`path` dependencies.
- Electron now runs the renderer with `nodeIntegration: false` and
  `contextIsolation: true`; controller startup is a browser page script, and
  preload exposes only the narrow `keposBackend` and `keposDesktopConfig` APIs
  through `contextBridge`.
- The controller still runs in the renderer process for the non-Electron/local
  fallback path.
- Electron main now has a worker-shaped backend host boundary. The current host
  can consume either the deterministic in-process stream fallback or an external
  worker stream. Session creation has moved behind
  `src/desktop-backend-worker-entry.js`, and Electron main connects only to the
  IPC client bridge returned by the host's async `start()` lifecycle.
- The non-smoke Electron path now wires `pear.run()` to the bundled worker entry,
  and the dedicated Pear desktop smokes prove the app-level path can boot,
  publish QR snapshots, create a Home, send Home chat, create an owner Treehole
  post, trust a Profile QR contact, persist that ContactBook state across
  restart, create a Direct message request to that persisted contact, revoke the
  contact, prove the Direct request remains visible after restart, prove the
  revoked trusted contact stays hidden after restart, and render backend state
  feedback.
- Desktop and Android now use the same Direct session restoration model for
  message request display state. Desktop stores request-session rows through the
  profile storage adapter; Android stores the same request-session rows in
  app-private file storage and restores them when creating or joining a home.

This means the UI is product-shaped and the desktop runtime boundary has crossed
the basic app-level proof bar. The remaining release bar is broader product
proof: cross-device runs, restart behavior, failure handling, and longer
sessions through the same bridge. Keep the fast in-process desktop smoke as a
deterministic fallback gate, and use the Pear/Bare desktop smokes plus debug
cross-device smokes when changing bridge-sensitive runtime code.

### 2. Desktop Dynamic Lists Are React-Owned

Status: done for the main dynamic list surfaces.

React owns the stable desktop shell, Home chat list, Direct message list, Direct
message trusted-contact picker, People lists, Treehole post/comment rows, and
desktop status labels, plus the large QR dialog, inline share QR outputs, and
rail/pane active state, action/composer disabled state, and the Home chat,
Direct message, Treehole main post, and context-panel form drafts.

Home chat rows, People contacts/message requests, Direct message rows, Direct
message trusted-contact picker rows, Treehole post/comment rows, and status
labels now have separate view-model boundaries in
`src/desktop-home-chat-view-model.js`, `src/desktop-people-view-model.js`,
`src/desktop-direct-view-model.js`,
`src/desktop-direct-contact-picker-view-model.js`, and
`src/desktop-treehole-view-model.js`, and `src/desktop-status-view-model.js`.
These surfaces feed React components through the renderer UI bridge.

Repeated content, status, navigation, QR display, shell actions, busy state,
disabled-state, Home chat draft, Direct message draft/recipient, Treehole main
post draft, and context-panel form draft surfaces no longer require imperative
DOM construction.

The current React shell has first-pass MLP polish for theme, focus, hover,
navigation, and narrow-screen layout. Remaining desktop UI work should keep
React fed by snapshots, drafts, and explicit command payloads instead of adding
controller DOM listeners back.

### 3. Live Cross-Device Proof Remains Debug-Heavy

Status: acceptable for iteration, not final proof.

The debug two-device smoke proves live transport behavior, but part of the path
uses debug setup rather than the fully normal physical QR flow. The Pear/Bare
variant now lets the same debug cross-device path run with the desktop side on
the bundled worker bridge. Manual physical QR evidence covers the
screen-to-camera Profile QR and Home QR path.

Release-readiness evidence should include manual smoke for final V1 confidence,
plus `smoke:two-device:debug:pear` when desktop bridge changes need
cross-device evidence. Avoid making fragile smoke work the main implementation
thread unless the work is specifically release proof.

## Non-Blocking For V1

These are not V1 blockers:

- desktop camera scan
- key rotation after revoke
- compact binary QR payloads
- multi-device identity
- safety-number compare UX
- V2 listening/watch room features
- V3 RetroArch or local service tunnels

## Next Best Work

The next implementation phase should close concrete gaps found by gates,
manual smoke, debug cross-device smoke, or PR review. The broad architecture
shape is in place: React-owned product surfaces, backend bridge snapshots,
signed trust and treehole rules, durable Direct threads, Direct request restart
display on desktop and Android, and Pear/Bare desktop worker proof. The
highest-value remaining V1 work is evidence-driven hardening: cross-device
repetition, restart behavior, failure handling, and any product-path defects
those runs expose.
