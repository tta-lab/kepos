# V1 Ready IM Completion Plan

This document is the V1 completion and release-evidence checklist.

Most implementation items named here now have source-level or automated-test
evidence. The remaining bar before V1 should be called ready is final
desktop/Android release proof on real product paths, not a new feature list.

The target is not "a demo that can send messages." The target is a small,
lovable private IM product built on the P2P infrastructure:

```text
profile -> friend request -> mutual trust -> Chat / Profile / Home / Treehole
```

V1 should feel like a private QQ or WeChat for a tiny trusted circle, with P2P
as the base rather than as the visible product concept.

## Scope Lock

Everything in this document is V1 scope.

These items are not V2 features, not optional polish, and not "nice later"
ideas. V2 can add listening rooms, watch rooms, richer media, presence, and
multi-modal spaces. V1 still must first become a complete private IM:

```text
friends -> durable messages -> profile context -> personal posts -> explicit Home entry
```

If a task is required for that sentence to feel true, it belongs in V1.

## Product Bar

V1 ready means a user can:

- create their profile once
- add a friend by scanning or pasting a Profile QR
- send a friend request
- accept or ignore a friend request
- see the friend in Contacts
- open a durable Chat thread
- send and receive Chat across restart
- see their own Treehole as a durable posting surface
- open a trusted contact profile
- see enough profile context to understand who this person is
- enter that trusted contact's Home when they choose to
- remove a friend and stop future access

V1 should not require users to understand room keys, transport topics, raw
profile ids, raw Home QR text, or debug DM fallbacks in the normal path.

## Self Review Verdict

Current V1 is close, but release readiness is not yet proven.

The architecture is no longer just a throwaway P2P chat demo: identity signing,
ContactBook state, DM thread persistence, treehole authorization, request-bound
trust, revoke, and desktop/mobile product labels now form a coherent V1 product
shape.

Remaining evidence gaps are now narrower:

- Profile detail exists on desktop and Android for trusted contacts and
  request-target previews; final smoke still needs to prove the full profile
  path with real peers.
- Friend request state is now more legible: incoming, outgoing, trusted,
  removed, and ignored states have visible Contacts surfaces on desktop and
  Android. Removed/ignored profiles now have an explicit `Allow requests`
  recovery action that permits a new request without restoring prior trust.
- Chat has persisted inbox rows and direct message bubbles with generated
  avatar placeholders, labels, preview, time, accepted/request state,
  latest-activity ordering, selected-thread focus, incoming request row
  actions, and persisted read-marker unread badges. A fuller dedicated thread
  screen remains layout polish, not a V1 blocker.
- `Enter Home` is visible and live when a trusted contact has a saved Home
  descriptor.
- Desktop and Android Home surfaces now show whose Home is active. The shared
  Home owner view-model labels `My home`, a trusted contact's Home, or a short
  owner fallback, and the Home bar can open the owner profile when the owner is
  a trusted contact.
- Desktop and Android navigation labels now share the typed product-surface
  vocabulary in `src/product-surfaces.ts`, keeping `Home`, `Chat`, `Contacts`,
  and `Treehole` aligned across rail, tabs, and active-surface
  copy.
- Desktop and Android Treehole empty copy now respects the owner-only post
  rule: owners are invited to write the first post, while viewers who cannot
  post see neutral "posts from this Home" copy.
- Android composer text normalization now uses the typed helper in
  `src/composer-text.ts`, so Home, Chat, and Treehole share the same
  trim/blank-write behavior before RPC dispatch.
- Desktop and Android transport debug labels now share the typed formatter in
  `src/transport-debug-label.ts`, with Android opting into its extra
  `directReady` diagnostic.
- `Recent posts` can show real loaded Treehole posts for the trusted profile
  whose Home is currently joined, and desktop/Android keep a durable
  per-profile cache after visiting a Home. Trusted profile details now expose an
  explicit `Refresh posts` action when a usable signed Home descriptor exists;
  it reuses the same checked Enter Home path instead of silently entering Homes.
- Real avatar URI snapshots can now travel through signed Profile QR payloads,
  ContactBook `avatarUriSnapshot`, profile/detail/message view-models, and
  desktop/Android avatar rendering, including Profile QR request-target
  previews before trust exists. Desktop and Android now also have local avatar
  import plus first-pass verified avatar byte sync over Home control.
- Local profile storage persists the local `avatarUri`, desktop and Android
  both expose a local avatar URI setting, and Show My QR emits that avatar URI
  through the signed Profile QR payload when one is present.
- Desktop and Android now have source-level parity for the normal names and
  core states. The remaining parity risk is final real desktop/Android smoke,
  not a known missing source path.
- The current non-device V1 gate is green: `npm run v1:gate` passes lint,
  typecheck, 902 Node tests, TypeScript compatibility probes, desktop bundle
  generation, Bare Android bundle checks, Expo Android export, and Android APK
  native-library checks.
- The standalone Android release APK path is also scripted and green:
  `npm run android:assemble:release` builds `app-release.apk` and runs the same
  native-library check against that release artifact.
- Storage cleanup tooling exists; final cross-device proof is still unfinished.

The next work should not start V2. It should close the remaining V1 evidence
gaps and fix any source issues revealed by that proof.

## Completion Evidence

### 1. Real Profile Detail Screen

Current state:

- Contacts opens a per-contact profile detail surface on desktop and Android.
- The detail shows `Message`, `Enter home`, `Recent posts`, metadata, stable
  avatar placeholder, remove friend, and advanced identity details.
- Android trusted-contact rows now act as a single profile entry point instead
  of nesting action buttons inside the list row. This keeps the Contacts list
  scannable while preserving Message, Enter Home, Recent posts, Remove friend,
  and Advanced identity in the profile detail.
- Android now keeps full profile fingerprints behind an `Advanced identity`
  toggle in the profile detail, matching the desktop advanced identity fold.
- Desktop and Android Chat thread rows can open the same contact profile
  detail.
- Android profile-scan request previews can open a limited profile detail for
  the scanned request target before trust exists.
- Desktop Profile QR paste results now show the same request-target preview
  card in Chat and can open a limited profile detail before trust exists.
- Desktop and Android contact rows now share `src/contact-profile-view-model.ts`
  for display name, short profile id, trust labels, action labels, Home entry
  availability, and Recent posts copy.
- Trusted and limited profile detail models now use the same normal-flow
  `Enter Home` action label on desktop and Android, matching the V1 product
  surface vocabulary.
- Trusted contact removal now uses `Remove friend` on desktop and Android
  list/detail actions, with `Friend removed.` as the success notice. The model
  and protocol still use revoke terminology internally.
- Desktop and Android limited Profile QR request-target details now share
  `src/request-target-profile-view-model.ts`, keeping untrusted profile detail
  copy and avatar rendering aligned before a friend request becomes trust.
- Limited Profile request details now keep `canRemove` false and use a neutral
  `Request pending` non-action label, so untrusted profiles do not carry
  `Remove friend` copy before friendship exists.
- Desktop and Android trusted contact profile details now share
  `src/profile-recent-posts-view-model.ts` for the first Recent posts behavior:
  show the active joined Home owner's loaded Treehole posts on that owner's
  profile.
- The same view-model now accepts a per-profile recent-post cache. Desktop and
  Android update that cache when a joined Home publishes non-empty Treehole
  posts, so the contact profile can still show those posts after leaving the
  Home during the same app run.
- The cache is now durable. Desktop stores it in local key-value storage, and
  Android stores it in app-private file storage as normalized post summaries
  rather than raw Treehole objects.
- Corrupt optional Recent posts cache data is dropped as an empty cache instead
  of blocking startup on desktop or Android.
- Corrupt optional DM session request-row cache data is dropped as an empty list
  instead of blocking startup; ContactBook remains the pending-request authority.
- Corrupt optional profile snapshot history is dropped during ContactBook
  restore while contact identity, trust, and request fields remain strict.
- Desktop and Android profile details now show a `Refresh posts` action in the
  Recent posts section when the trusted contact has a usable signed Home
  descriptor. The action deliberately goes through `Enter Home` so owner proof,
  local trust, and descriptor expiration stay enforced.

Needed:

- Final product smoke should verify the `Refresh posts` action loads posts from
  a trusted contact's Home on desktop and Android.

Why:

Contacts is an address book. A profile detail screen is the user's mental model
for "this person."

### 2. Friend Request UX Completion

Current state:

- Outgoing friend requests are stored.
- Outgoing friend requests are visible in desktop and Android Contacts as
  `Sent requests`, and Contacts badges include them.
- Request-bound invite acceptance completes the requester side of mutual trust.
- Android active-home Profile QR scan can become a friend-request target.
- Desktop Profile QR paste becomes a friend-request target and selects Chat.
- Desktop and Android both show a scan/paste result preview that can open the
  target profile.
- Desktop and Android scan/paste previews now share one relationship-state
  model:
  - new profile -> allow request message
  - outgoing request exists -> show pending copy and block duplicate send
  - incoming request exists -> point to Contacts
  - ignored or revoked -> show blocked copy and block send
  - already trusted -> show existing-friend copy
- Android normal Profile QR scan/paste no longer creates direct trust. It only
  selects a friend-request target in Chat; the old direct-trust helper is
  named as debug-only support code.
- Removed and ignored contacts no longer disappear from the user's mental
  model. Desktop and Android Contacts show a `Removed / ignored`
  section backed by the ContactBook `revokedAt` and `requestIgnoredAt` fields.
  Removed copy says future access is stopped and does not imply already-copied
  data is erased.
- Desktop and Android expose `Allow requests` from the `Removed / ignored`
  section. This clears the local request block so a fresh friend request can be
  made, but it deliberately does not restore trust, Home access, saved Home
  descriptor fields, or prior proof data.
- `Request pending` state is now restart-proof in the non-device gates:
  ContactBook sync storage and Android file storage persist outgoing friend
  requests, desktop startup publishes the restored ContactBook snapshot, and
  Android derives the `Sent requests` panel from the restored ContactBook.

Needed:

- Final cross-device proof should still include the `Request pending` restore path
  and `Allow requests` recovery path as part of the release smoke, but the
  storage/startup/UI contracts are now covered by automated non-device tests.

Why:

Friend request is now the authorization entry point. It must feel complete, not
like a side effect of sending a Message.

### 3. Chat Thread List As Real Inbox

Current state:

- Desktop and Android can show accepted thread rows.
- Desktop and Android rows now share one thread-list view model with contact
  label, latest-message preview, time label, accepted/request state, and
  latest-activity ordering.
- Desktop and Android thread rows show the same deterministic generated avatar
  placeholder as contact/profile surfaces.
- Desktop and Android direct message bubbles show deterministic generated
  avatars for the local user and incoming sender.
- Selecting a row switches the active recipient and shows a current-thread
  header above the conversation on desktop and Android.
- Desktop and Android focus the visible message list on the selected direct
  thread. Chat messages from other peers remain represented in inbox rows but no
  longer mix into the current conversation view.
- Desktop and Android now use the same `src/dm-thread-list.ts` selected-thread
  lookup helper, so the current-thread header and composer placeholder resolve
  the active profile the same way on both platforms.
- Local Home message, friend request, accepted-thread, and Treehole interaction
  ids now use `src/secure-id.ts`; Android passes Expo secure random bytes, and
  desktop defaults use WebCrypto instead of `Math.random()` fallbacks.
- Home room keys now use the same secure-random boundary for fixed-width
  32-byte hex keys and fail closed when WebCrypto random bytes are unavailable.
- Requested rows now stay visible in the inbox as `Request pending`, using
  request time for ordering when no message exists yet.
- Incoming requested rows now expose Accept and Ignore actions directly in the
  desktop and Android inbox. Outgoing pending rows remain passive waiting rows.
- The shared thread-list view model can compute unread incoming counts from
  explicit `lastReadAt` markers, and desktop/Android rows render the unread
  badge when that marker exists. Desktop and Android persist local read markers
  in DM thread state when a thread row is opened.
- Desktop preload/main/worker backend paths now publish DM thread snapshots
  through `dmThreadChanged`, so thread rows are available outside the local
  renderer runtime fallback.
- Desktop and Android empty thread lists now point users to Contacts, where they
  can scan a profile or accept a friend request.
- Chat messages persist across restart.

- A fuller dedicated thread screen would still be cleaner later, but the normal
  V1 path now behaves as a real thread view and no longer depends on seeing or
  editing a raw recipient id.
- Pear desktop smoke scripts cover the bundled worker bridge for the current
  source shape. Final release proof should rerun that worker path, but this is
  no longer an unproven source-level Chat gap.

Why:

This is the center of an IM product. If Chat feels thin, the whole product
feels like infrastructure.

### 4. Signed Home Descriptor, Not Home Invite

Current state:

- Home QR / home address exists as a transport entry mechanism.
- Product language is moving away from Home QR as the trust path.
- Desktop and Android normal copy no longer calls Home QR a Home invite. The UI
  uses `Home QR` for the advanced transport detail and `Home access` for saved
  trusted entry.
- Android quick-start no longer teaches Home QR as the normal sharing path. The
  compact start panel shows `Show My QR` for the profile/friend-request flow and
  `Open Contacts`; Home QR scan/show remains in Advanced transport controls and
  release smoke helpers.
- Android Advanced Profile request controls now use the same `Show My QR` reveal
  label as quick-start, so one profile QR action does not have two visible
  names.
- Desktop now exposes `Show My QR` in the normal Home context next to `Open my
home`, reusing the signed Profile QR dialog as the friend-request entry point.
  Advanced Profile request controls use the same reveal label while keeping
  Profile QR details and copy controls under Advanced.
- Desktop Home QR show/copy/paste controls now sit behind the Home context
  `Advanced` fold, so the default Home panel no longer presents Home QR as a
  normal entry path.
- Remaining visible setup copy now says `Contacts` on desktop and Android. The
  internal `People` component and route names remain as implementation names,
  but normal users see the address-book model.
- Desktop can now store a signed Home descriptor on an already trusted contact
  when a signed Home QR is scanned/pasted.
- Signed Profile QR can now also carry an optional, independently signed Home
  descriptor owned by the same profile. Scanning it prepares a friend-request
  target, carries the descriptor into outgoing friend request state, and stores
  it only after trust exists.
- Desktop and Android Show My QR now generate that optional descriptor from the
  local Home address/room key when a Home exists, so Profile QR is the normal
  refresh path for trusted Home transport metadata.
- Desktop `Enter home` now reads the saved descriptor through the shared
  descriptor validator before joining. The validator requires a saved
  descriptor, local trust toward the owner, and a Home address proof signed by
  that owner.
- Android can now store the same descriptor and route `Enter home` through the
  same shared descriptor validator before joining.
- Desktop and Android contact/profile view models now keep `Enter Home`
  disabled unless the saved Home descriptor has address, room key, owner proof,
  and no local expiration. The UI no longer presents stale or incomplete
  transport metadata as a usable Home entry.
- A tampered saved descriptor, such as a room key that no longer matches the
  saved proof, is rejected before the join session is created.
- Descriptor expiration now round-trips through ContactBook storage and is
  enforced when a saved descriptor is read for entry.

Decision:

Friendship/trust is the permission. A Home descriptor is not authorization.

The needed object should be understood as:

```text
signed home descriptor = where this trusted profile's Home can be reached
```

It should not be presented as:

```text
home invite = permission to enter
```

Needed:

- Keep the signed home descriptor payload owned by the profile.
- Desktop and Android already store signed Home descriptors learned from Home
  QR scan/paste for trusted contacts.
- Desktop and Android now also refresh/update that descriptor through the
  normal profile-owned Profile QR path. The descriptor is separately signed and
  verified, so the Profile QR invite proof encoding remains compatible with old
  QR payloads.
- `Enter Home` already reads the trusted contact's descriptor, verifies owner
  signature, checks local trust, and joins only after explicit user action in
  the desktop and Android source paths covered by non-device tests.
- Final real-device proof must verify this across desktop and Android.
- Existing Home QR can remain an advanced/debug way to copy or inspect the
  descriptor, not the normal social flow.

Why:

The user model is "I trust this person, so I can enter their Home." The transport
still needs connection data, but the data must not become a second permission
system.

### 5. Recent Posts From Trusted Profiles

Current state:

- Treehole exists as a durable posting surface.
- Contact rows show `Recent posts` copy.
- Trusted contact profile detail shows real recent posts when that contact owns
  the currently joined Home and the active Treehole state has posts.
- Desktop and Android cache the last non-empty recent posts per profile in
  durable local storage, so leaving a Home or restarting the app does not
  immediately empty that profile's Recent posts.
- Desktop and Android profile details expose explicit `Refresh posts` from the
  Recent posts section when signed transport metadata is available. This is the
  V1-safe refresh path: the user opts in, then the existing Home join, signed
  hello, treehole bootstrap, and local cache update path does the sync.

Needed:

- It does not need to be a global feed in V1.
- It must respect trust policy:
  - trusted contacts can read
  - pending/untrusted contacts cannot read private posts
  - revoke blocks future reads but does not delete old local replicated data
- Final cross-device smoke should prove refreshed posts appear after the remote
  Home shares treehole bootstrap data.

Why:

Treehole gives the product personality. Without Recent posts on profiles, it
feels like a separate tab instead of part of the social graph.

### 6. Contact And Trust State Polish

Current state:

- Trust, pending requests, outgoing requests, ignored requests, and revoke exist
  in the model.
- Contacts now clearly separate trusted friends, incoming requests, outgoing
  requests, and removed/ignored profiles on desktop and Android.
- Removed/ignored profiles can be reopened for new requests through
  `Allow requests`; this is not a trust restore.
- Removed friend copy now states that future access stops while already-copied
  data is not erased.
- Contact/profile display names now prefer local alias, then remote display
  name, then `Profile <short id>`. Full raw profile ids stay in advanced
  identity details, with Android also keeping the full fingerprint collapsed by
  default.
- Incoming Android friend requests do not persist short profile ids as aliases;
  the stored contact/request keeps alias empty unless a real local alias or
  remote display snapshot exists, and the UI renders `Profile <short id>` or
  `Someone` as the fallback.
- Unknown/manual trust-source labels now render as `This device` / `From this
device` instead of exposing `local trust` in normal Contacts and profile UI.
- Treehole author fallbacks now use `Profile <short id>` or `Someone` instead
  of exposing the internal `anon` default in normal post and comment UI.
- Chat peer fallbacks now use `Profile <short id>` when identity is known
  and `Someone` when it is not, instead of showing debug-style unknown ids in
  normal message metadata.
- Desktop's manual recipient id field is explicitly labeled `Manual recipient
profile id` and remains under Advanced, keeping normal Chat use centered
  on contacts and thread rows.

Needed:

- Final product smoke should verify the same copy and name fallback on real
  desktop and Android screens.

Why:

Trust is the security boundary. The UI must make state legible.

### 7. Profile And Avatar Basics

Current state:

- Display name exists.
- Stable generated avatar placeholders still exist in
  `src/profile-avatar-view-model.ts` as the fallback.
- The signed Profile QR payload can carry an optional avatar URI, and
  ContactBook stores `avatarUriSnapshot` for trusted contacts and pending or
  outgoing friend requests.
- ContactBook also stores `avatarMediaSnapshot` beside that URI snapshot for
  trusted contacts and pending/outgoing request state, and trusted-contact
  lists expose it to UI code after avatar bytes have been verified and stored.
- Shared avatar view-models can prefer a platform-resolved local URI from
  `avatarMediaSnapshot` over the raw avatar URI fallback, so verified avatar
  media can render in contact profiles and Chat inbox rows without each UI
  surface inventing its own resolution rule.
- `src/avatar-media.ts` now exposes `createAvatarMediaUriResolver`, so desktop
  and Android can use the same app-private storage URI rule when they render
  verified downloaded avatar bytes.
- Desktop Chat recipient chips and direct message bubbles pass stored
  avatar media references through that shared resolver hook.
- Mobile Chat recipient chips and direct message bubbles now follow that
  same resolver hook, so the main IM surfaces on both platforms can render
  verified local avatar media once local bytes are present.
- Profile QR request-target previews and limited request-target profile details
  now share the same avatar media resolver model, keeping pre-trust profile
  surfaces aligned with trusted contact/profile rendering.
- Local profile storage persists the local `avatarUri` plus optional
  `avatarMedia` reference. Android's profile document and runtime bootstrap
  preserve the same media reference, and both desktop share QR generation and
  Android Show My QR include it in the signed Profile QR payload when present.
- Contacts, Chat thread rows, direct message bubbles, Treehole author rows,
  Chat recipient chips, Profile QR request-target previews, and Profile
  detail use avatar view-models on desktop and Android; real image URIs render
  when present, otherwise the UI falls back to generated initials.
- Desktop and Android direct message rows now prefer the local contact snapshot
  for the remote profile display name and avatar URI, then fall back to the old
  message nickname and generated avatar seed. Existing durable messages
  therefore keep rendering with the user's current local alias and latest local
  avatar snapshot after a profile name changes.
- `src/avatar-media.ts` now defines the V1 content-addressed avatar media
  reference contract. It records `kepos.avatar.media.v1` references with
  `sha256` digest, MIME type, byte length, stable `kepos://avatar/sha256/...`
  URI, fail-closed image type/size/digest validation, and app-private avatar
  media storage paths under `kepos/v1/avatar-media/sha256`. Downloaded avatar
  bytes can be checked against the reference before storage or rendering, which
  is the verification hook needed by the later P2P byte-sync path.
- Signed Profile QR now has a compatibility-safe avatar media metadata path:
  raw-avatar-only Profile QR stays on `kepos.trust.invite.v1`, while Profile QR
  with a signed avatar media reference uses `kepos.trust.invite.v2`. The scanner
  verifies the media reference as part of the signed payload, rejects tampering,
  exposes it on the request target, and stores it on the trusted contact.
- Desktop share QR generation and Android Show My QR pass an existing local
  profile `avatarMedia` reference through the signed Profile QR payload when
  present.
- Desktop and Android outgoing friend-request writes preserve the request
  target's display name, raw avatar URI, avatar media reference, and signed Home
  descriptor so request-sent rows can recover the same profile context after
  restart.
- `src/avatar-media-storage.ts` now provides the shared byte-storage boundary:
  it writes avatar bytes only after reference verification, reads stored bytes
  back through the same check, and treats missing or mismatched bytes as absent
  media.
- It also provides a string file-system adapter for Expo-style
  `readAsStringAsync` / `writeAsStringAsync` storage, encoding avatar bytes as
  base64 through the shared b4a-backed default codec while still feeding the
  verified byte-store API.
- `src/profile-avatar-import.ts` provides the shared import boundary for the
  platform picker and P2P receive slices: it turns image bytes plus MIME type into
  a content-addressed `avatarMedia` reference, stores the bytes through the
  verified byte-store API, and returns `avatarMedia`, `avatarUri`, and the local
  storage URI for profile state updates.
- Desktop now has the first real platform picker integration. The React context
  panel can choose a local PNG/JPEG/WebP file, send base64 bytes through the
  `updateAvatarMedia` desktop command, write verified bytes under app-private
  desktop storage with `src/desktop-profile-avatar-media.ts`, persist the local
  `avatarMedia` reference, and include that signed reference in Show My QR.
- Android now has the matching real platform picker integration. QuickStart can
  choose a local image through Expo image picker, `src/mobile-profile-avatar-media.ts`
  reads and stores verified bytes through Expo FileSystem, persists the local
  `avatarMedia` reference, and Android Show My QR includes that signed reference.
- `src/avatar-media-sync.ts` defines the first cross-peer avatar byte sync
  frame. It is deliberately subordinate to signed Profile QR metadata: bytes are
  stored only when the local ContactBook already has the same
  `avatarMediaSnapshot` for that profile.
- Desktop Home control now sends local verified avatar bytes after a verified
  Home hello and stores received bytes through the same reference check. This
  gives desktop peers real avatar byte exchange without making bytes themselves
  an authorization source.
- Android Home runtime now uses the same frame through a UI/backend bridge:
  `src/mobile-avatar-media-sync.ts` builds a local avatar-media control from
  app-private Expo FileSystem bytes, passes it to Bare backend at Home startup,
  backend sends it after verified Home hello, and incoming avatar media controls
  return to the UI for ContactBook-gated verified storage.
- `src/profile-snapshot.ts` now defines the minimal local versioned profile
  snapshot model. ContactBook stores those snapshots when a friend request or
  trust update carries display/avatar metadata, persists them through normal
  ContactBook storage, deduplicates display-equivalent updates, and keeps DM
  inbox rows able to fall back to the latest captured profile snapshot.

Needed:

- Full signed profile records or profile-feed streaming remain future work. The
  V1 local snapshot base is in place; it should not be expanded into a new
  protocol until the full profile record shape is deliberately designed.

Why:

IM needs human recognition. Raw ids and text-only rows feel unfinished.

### 8. Desktop / Android Parity

Current state:

- Most source-level product behavior has parity.
- Desktop preload/main/worker paths now expose DM thread snapshots for the same
  Chat list as the local fallback path.
- Android has camera scan; desktop mostly paste/show QR.
- Desktop visible and accessibility copy now uses the V1 product names for the
  normal Chat and Treehole surfaces: `Chat`, friend request actions, and
  `Post to Treehole`.
- Desktop and Android Profile request QR input copy now says `Profile QR`
  instead of the older `Friend profile`, keeping the request flow aligned with
  the shared V1 surface names.
- Desktop and Android both expose Profile QR request-target previews. Desktop
  paste and Android scan/paste select Chat, show the request-target card,
  and can open the limited profile detail before trust exists.

Needed:

- Keep the same normal flow names on both platforms: Contacts, Chat, Treehole,
  Profile request, and Enter Home.
- Keep the same core states on both platforms: request target, request sent,
  incoming request, trusted, and revoked.
- Desktop preload/worker path should keep closing any remaining state gaps that
  appear during final smoke, but DM thread snapshots are no longer local-only.
- Final smoke should prove the real desktop and Android paths match the
  source-level parity already recorded here.

Why:

V1 should feel like one product, not two demos sharing protocol code.

### 9. Persistence And Storage Hygiene

Current state:

- Profile, contacts, DM sessions, DM threads, treehole state, and home keys have
  persistence pieces.
- Smoke/dev runs have created storage-size concerns.
- `npm run storage:cleanup` now provides a dry-run cleanup path for leftover
  desktop smoke temp dirs, explicit desktop Electron `userData` cleanup, and
  Android app data reset through `adb shell pm clear io.guion.kepos`.
- Desktop smoke temp dirs are disposable by construction: smoke scripts create
  them under the OS temp directory and write a `.kepos-smoke-storage` marker.
  Cleanup only selects known smoke-name prefixes when that marker is present.
- Destructive cleanup requires both `--apply` and
  `--i-understand-this-deletes-kepos-data`.

Needed:

- Keep using the cleanup tool instead of ad hoc `rm -rf` or manual app-data
  guessing.
- Keep durable user data and disposable test data in separate paths.
- Add visible in-app reset/debug cleanup tools only if manual V1 smoke shows
  that command-line cleanup is not enough.
- Keep corrupt data fail-closed behavior.

Why:

An IM app is trusted with personal history. Storage must be predictable before
calling V1 ready.

  Android bundle generation, Expo Android export, APK native-library alignment,
  and desktop bundle generation for the React app, browser controller, Node
  controller, local backend, local profile helper, Tailwind/daisyUI CSS, and

## Dependency Order

Recommended order:

1. Signed home descriptor model and storage.
2. `Enter Home` from trusted contact profile.
3. Real profile detail view on desktop and Android. Done for Contacts,
   Chat thread entry points, and Profile QR request-target previews.
4. Friend request preview and outgoing request states.
5. Chat thread list polish: generated avatar context, current-thread
   header, focused selected-thread message lists, requested-row state, incoming
   request row actions, direct bubble avatars, and persisted read-marker unread
   badges are done; a fuller dedicated thread screen remains as layout polish.
6. Recent posts on trusted profile. Active-Home rendering, durable per-profile
   cache storage, and explicit profile-detail refresh through signed Home entry
   are done. Final cross-device smoke still needs to prove the refresh path with
   real peers.
7. Avatar / profile snapshot basics. Generated placeholder fallback, signed
   avatar URI snapshots, local avatar URI settings, ContactBook
   `avatarUriSnapshot` / `avatarMediaSnapshot`, desktop/Android image
   rendering, shared avatar media resolution hooks, and the content-addressed
   avatar media reference contract are done; desktop/Android local picker import
   is done; desktop and Android Home-control byte sync are done; minimal local
   versioned profile snapshots are done.
8. Desktop preload/worker parity for thread/profile state. DM thread snapshots
   are done; final worker smoke may still reveal smaller state gaps.
9. Storage hygiene and cleanup tools.
10. Final cross-device smoke.

This order keeps the architecture honest:

- trust remains the authorization SSOT
- profile remains the social entry point
- Home descriptor remains transport metadata
- Chat becomes the daily-use surface
- Treehole becomes profile content, not a protocol console

## V1 Non-Goals

Do not pull these into V1:

- multi-device account linking
- global username discovery
- public feeds
- group chat
- V2 listening/watch rooms
- V3 local service tunnels or RetroArch sessions
- full OPSEC claims
- remote deletion guarantees after revoke

V1 should be narrow and solid: private profile, friends, durable messages,
personal posts, explicit Home entry.
